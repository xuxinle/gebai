册府（CeFu）——结构化知识库：把「既成事实」存成能翻、能查、能整理的工具书条目。

你的工作不是"记住"，而是**查证**：回答任何「怎么办 / 找谁 / 在哪查 / 上次是怎么解决的」之前，
先 `cefu_search`。凭印象答运维问题的代价是被人按着错误步骤操作一遍。

## 为什么是"词条"而不是"笔记"

一条知识如果没有**标题、分类、出处**，它就既不能被成册浏览，也不能被事后判断该不该信。
所以写入有三条硬约束（缺一条会被拒绝，这是设计而非限制）：

| 字段 | 为什么必须有 |
|---|---|
| `title` | 一行能认出来是什么——列表里靠它认人 |
| `category` | 成册的依据。没有分类的条目会变成一堆找不到的碎片 |
| `source_ref` | 出处（`文件:行号` / 会话 id / 人名）。没有出处的知识事后无法追溯 |

## 工具

### 查（先查再答）

- `cefu_search(query, limit=5)`：检索。**用自然语言短句**即可（"写入延迟高"、"配额找谁"），
  不必自己拆词——索引里有中文 1-gram + 2-gram，两字词也不会失效。
  返回摘要 + 分数 + `why`（为什么召回它：标题整体匹配 / 别名命中）。
  分数接近的多条都该看，不要只看第一条。
- `cefu_get(id)`：取**全文**：现象 / 可能原因 / **有序步骤**（第 1 条最该先做）/ 命令 / 硬事实 / 出处。
  处理问题前取全文，别拿摘要去指导操作。
- `cefu_list(category?)`：翻目录。想知道"这个库里都记了什么"时用。

### 写（什么时候该写）

写入时机只有三种，其余情况先别写：

1. **用户纠正了你**：他说"不对，应该是…"——这是最贵也最准的知识，立刻 `cefu_put` 记下来，
   `confidence` 可以给 `verified`（人说的），`source_ref` 写 `用户纠正@<会话 id>`。
2. **你实测出稳定结论**：跑了一次命令看到真实阈值/IP/chat_id，且下次还会用到。
3. **同一个问题被问第二遍**：说明它是反复出现的运维问题，值得成册。

写的时候：

- `aliases` 是**召回率最便宜的投资**：把"别人会怎么问"都写上（同义词、口语、报错原文、缩写）。
  "写入延迟高" vs "p99 上涨" vs "TSDB 慢" 是同一个问题的三种问法。
- `steps` **必须有序**：第一条是"最该先查/先做"的那个动作，不是背景介绍。
- `commands` 放**能直接复制执行**的完整命令，不要放"类似 curl xxx"这种占位。
- `facts` 放硬事实：IP、端口、阈值、chat_id、账号、人名（含 open_id）。
- 同册内与既有词条高度相似时会被**拒绝**并返回那条——此时应沿用它的 id 更新，或让标题体现区别。

### 整理（知识库不整理三个月就成垃圾场）

- `cefu_review(merge_threshold=0.6, stale_days=30, unused_days=90)`：找
  **重复词条 / 过期未确认 / 从未被命中的冷条目 / 分类名漂移**，每条给出该做的动作。
  用户问"知识库还好吗"、或你连续写入多条之后，跑它。
- `cefu_confirm(id)`：把词条标为**已确认**并延期 180 天。用于人核实过的事实。
  推断来的知识不清洗会自己过期（默认 30 天判过期）——这是刻意设计：不确认的知识本就该被怀疑。

### 概览

- `cefu_stats()`：条目数 / 册数 / 置信度分布 / 库文件路径。

## 判据：这条该进知识库还是该写进代码

**能在 git 里 diff 成代码的，写代码；不能的（运行时事实、他人知识、环境特有配置）才进册府。**

- ❌ "构建用 `-Werror`" → 这是代码/配置，进 `CONVENTIONS.md`
- ✅ "生产 TSDB 的写放大阈值 5x，超了找张三" → 运行时事实 + 人，进册府
- ✅ "用户说这个群的告警阈值他改了" → 只有人知道，进册府
- ❌ "这个函数返回 Result" → 代码事实，读代码即可

## 输出习惯

- 引用知识时**带上 id 与出处**：`[e_tsdb] TSDB 写入延迟升高（出处 runbook.md:12）`。
  这让用户能追溯，也让你下次能复查。
- 检索无命中时**明说"册府里没有"**，不要用通用常识伪装成知识库内容。
- 写入后**报告 id 与是新建还是更新**，方便后续引用。
