feat(bpy): 场景抽取 —— bpy 脚本 → ThreeScene

打通 bpy 脚本到渲染器的最后一段：抽取器把 `bpy.data` 里的场景转成
`ThreeScene`，与 three.js 那条路的下游完全一致。

判据 10/10 全过（`tools/bpy_scene_probe`）。

## 为什么抽取写在 Python 里

C++ 侧读 bpy 对象要逐层调 MicroPython API：三层深度的对象
（`obj.data.vertices[0].co.x`）就是四五次查表 + 类型检查，每个调用点
都要写错误处理——代码量极大且易错。

而 Python 侧写是自然表达：

    for v in obj.data.vertices:
        out.append(v.co.x)

所以分工是：**Python 理解 bpy，C++ 搬数据**（后者只做 dict → struct）。

```
bpy.data.reset()          ① 重置场景
      ↓
跑脚本                    ② 建出 bpy 场景
      ↓
_st_extract.extract_json()  ③ Python 抽取 → 扁平 JSON
      ↓
parse_extracted_json()    ④ C++ 搬进 ThreeScene
```

## 实现要点

| 文件 | 职责 |
|---|---|
| `src/python/extract.py` | 遍历场景、三角化、算世界矩阵、材质/相机/灯光 → JSON |
| `src/raster/bpy_runtime.cpp` | JSON → `ThreeScene`（纯数据搬运，无 bpy 知识） |
| `include/st/raster/bpy_runtime.hpp` | 对外契约 + 用法 |
| `parse_extracted_json` | 单独暴露给测试（不必每次跑 Python） |

## 抽取里三个容易错的地方（都钉进判据）

| 项 | 错法 | 症状 |
|---|---|---|
| 矩阵布局 | bpy 行主序 vs `Mat4` 列主序 | 位置对但旋转/缩放错位 |
| `fov_y` 单位 | bpy 弧度 vs `Camera.fov_y_degrees` 角度 | 视野极窄、只看到一角 |
| 灯光方向 | `Light.direction` 是**指向光源**（与相机 -Z 视线相反） | 物体被从背面照亮 |

这三条都不是"会崩"而是"画面有点不对没人报错"——所以探针用可断言的量
（顶点数、包围盒、材质值、fov 角度）把抽取钉住。

## 这轮修掉的问题

1. **输出缓冲 8 KB 太小** —— 场景 JSON 有数 MB，截断后报
   `JSON 解析失败（第 8192 字节）… unexpected end of input`，
   看起来像"序列化器写错了"，实际是**读回来时被截断了**。改 4 MB
2. **`MICROPY_PY_JSON` 在 MINIMUM 档没有** —— `import json` 报 ModuleNotFound。
   而抽取结果全是自己构造的简单类型，所以手写 60 行序列化器（无依赖、好查）
3. **`bpy.data` 跨 run 存活导致数据累积** —— 第二个脚本报
   `ValueError: 已存在同名数据块：'Cube'`，看起来像"脚本重名了"，
   实际是上一个脚本的残留。加 `bpy.data.reset()`，抽取器每次跑脚本前调
4. **`_Module.bind(...)` 误当方法** —— `bind` 是 `extract.py` 的全局函数，
   写成 `_st_extract.bind(...)` 报 `AttributeError: no such attribute`
   （而 `_Module` 是普通对象，那个报错不说是哪个属性）

## 已知边界（写进 docs/python.md）

- 面三角化用**扇形**：凸多边形正确，凹多边形会错（`primitive_*` 与 bmesh
  建的面绝大多数是凸的）
- 多材质只取第 0 个槽（本框架 `Mesh` 是单一材质）
- 父子关系不抽（`matrix_world` 已是绝对变换）
- 顶点留局部空间（变换由 `ThreeObject::world` 承担，两处都变换就是两遍）
