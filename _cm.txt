feat(bpy): 接入 scene3d_script —— bpy_script 三路并存

bpy 脚本现在能像 three.js 一样直接写进场景 JSON，端到端出像素。

## 三条表达路径（按优先级）

| 字段 | 优先级 | 说明 |
|---|---|---|
| `bpy_script` | 1 | bpy 源码（Blender Python API） |
| `three_script` | 2 | three.js 源码 |
| `objects` | 3 | 声明式 JSON（原有路径） |

### 自动识别（文本入口）

`parse_scene_spec_text()` 是裁云 `model_script` / 三维预览 / 自检三条路的
共同入口，按顺序分流：

1. 先试 JSON（合法且是对象 ⇒ 声明式）
2. 行首含 `import bpy` / `import bmesh` / `from mathutils` ⇒ bpy
3. 否则 ⇒ three.js

靠 import 语句而不是语法分析：真要做"Python 还是 JS"得写两个词法器，
而一个三维脚本不可能不 import 它的库。两个特征都稳。

### 渲染路径统一

两条脚本路**共用同一段**渲染代码（只在前三行决定取哪份 `ThreeScene`）：

    auto script_scene = bpy_mode ? BpySceneExtractor::extract(spec.bpy_script)
                                : ThreeRuntime::instance().evaluate(...);
    // 以下逐行相同：camera_override / extra_transform / material_override / end_frame

好处：裁云的镜头编排（推拉/机位/整体姿态/统一材质）**自动对 bpy 生效**
——否则要写两套，而那正是"改一处漏一处"的源头。

### 同时写两个脚本

不报错，**bpy 胜**，记一条 warn。理由：两者同时写一定是误操作，而模型从
两个例子各拿一段是常见情形；报错会让一份"其实能跑"的配置失败，给确定顺序
加警告更有用。

## 这轮修掉的问题

1. **`src/python/*.c` 从来没进过库目标** —— 探针各自显式列了它们，
   所以探针能跑；而 `st test` 的测试目标链不到 `st_mp_init` /
   `st_mp_deinit` / `st_mp_run`，报 `undefined symbol`。
   根因：`sources` 的通配 `src/python/*.cpp` 不含 `.c`（框架里 `.c`
   从不自动纳入源集合）。改成显式列出两个 `.c`
2. **相机/灯光被当 mesh 抽取** —— `obj.data` 是 `Camera` 对象，
   读 `.vertices` 抛 AttributeError，被外层 try 捕获成一条**假警告**。
   假警告会淹没真警告，所以加 `isinstance(mesh, Mesh)` 判型
3. **探针覆盖率判据恒 100%** —— 原判据拿传入的 `background` 比，
   但渲染背景经色调映射后会变，差值恒 > 阈值。改成拿**画布角落像素**
   作参照（背景是均匀的，角落就是背景色）

## 验证

`bpy_script_probe`：**7/7**

1. 纯 Python 文本自动走 bpy 分支（three_script 未被误填）
2. 出像素（非背景 18%）
3. 相机覆盖对 bpy 生效（18% → 52%）
4. 材质覆盖对 bpy 生效（亮红 17.9%）
5. 优先级 bpy > three
6. 错误路径可读

为何第 2 条必须用像素判据：`draw_mesh` 只提交到内部缓冲，合成到画布发生在
`end_frame`。漏了它，`draw_calls` 会涨、内部缓冲也有内容，但画布上一个
像素都没有（本仓实测过一次：抽取出 3 个方块、位置全对，像素计数为 0）。

- 另有：`bpy_scene_probe` 10/10、`python_embed_probe` 18/18
- 全量 17 分片 0 失败
