# 在途/池登记格式·多版本语料（只读夹具 + 等价性黄金基线）

> 本目录是 `shengsheng.test.ts`「版本化解析」一节的**只读语料**，**不是**运行态状态文件。
> 任何测试都不得回写这里的文件；与仓库根 `.evolve/control.md`（生生的运行态，工具托管）无关。

## 文件

| 文件 | 作用 |
|------|------|
| `01-new-header-mixed.md` | **新表头**（在途声明 6 列）而盘上躺着历代行：v1 残行 / v2 旧行 / v2 溢格旧行 / v3 自带列行 / v3 空会话列行；池表任务列含裸竖线 |

| `golden.json` | **等价性黄金基线**：`parseControl` / `renderControl` / 会话归属 / 往返结果，升级前实现捕获 |

## `golden.json` 的来历（**不要用当前实现重新生成它**）

它是在版本化解析重构**之前**（`fb53b33e` 的实现）由一次性脚本捕获的，用来把「与现有行为完全等价」
变成可执行断言，而不是「测试恰好绿」：

```
# 捕获（仅重构前跑一次，脚本不随包入库）
读取 fixtures/control-format-corpus/*.md →
  { state: parseControl(md),
    sessions: inflight.map(i => inflightSession(i, workers) ?? null),
    rendered: renderControl(state),        # 写入等价性：逐字节
    roundTrip: parseControl(renderControl(state)) }
写入 golden.json
```

用**当前实现**重新生成会让基线自动追随新行为，等价性断言随即失效——这正是它要防的事。
若日后**有意**改变解析行为（例如修正池表 v1 的历史读法），应把它当成一次显式的行为变更：
在用例里逐条说明差异、单独一单改 `golden.json`，而不是悄悄重跑生成脚本。

## 为什么语料要入库而不是合成行

合成行只会长成「写测试的人以为的样子」；真实盘上数据有历代渲染器留下的**裸竖线**（旧版不转义）、
**半截写入的残行**（格数不足）、以及**同表混排的多代行**（工具升级不迁移数据）。这些形态决定了判代
的四档证据与保守一侧的取舍，故语料要与用例一起演进：新增旧形态时先在这里加一格，再去测试里断言它。
