# 体裁：技术文档（设计 RFC / API 参考 / 故障诊断）

**读者任务**：评审者能批准并实现；调用者不用猜版本与行为；响应者能以安全动作缩小未知。

**先选唯一主模式**（三选一，不混写）

- `design_rfc`：问题证据 → 目标/非目标 → 约束与不变量 → 真实备选与同口径取舍 → 接口/数据/状态设计 → 失败·安全·兼容·迁移 → 上线与回滚 → 可观测性与验收 → 未决决定。每个关键决定写 why、被否方案与后果。
- `api_reference`：版本/环境/权限/签名 → 输入约束 → 行为·副作用·幂等 → 输出 → 已知错误与恢复 → 限流/分页/重试 → 兼容与弃用。未知语义写 unspecified，不从示例推断承诺。
- `incident_diagnostic`：影响与 expected/actual → 当前状态与证据链 → 可证伪假设 → 高信息增益低副作用的检查 → 止损与恢复验证 → 升级与后续 RCA。每项检查写预期观察及其支持/排除哪个假设。

**硬约束**
- 标对象、环境、版本、时间、范围与证据来源；事实、推断、决定、未知分开。
- 代码与命令须实际验证并标环境/版本；架构、状态、时序图必须附文字等价，不能成为唯一证据或唯一操作说明。
- 改状态的动作必须写授权、影响、停止条件、还原路径与恢复判据。

**常见错误**：按关键词路由或三模式混写；设计无取舍无验收；reference 漏权限/错误/生命周期/弃用；未知故障直接定根因。
