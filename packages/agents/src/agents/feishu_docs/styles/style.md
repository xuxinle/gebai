# 飞书文档排版总纲

写文档前读本文件；按体裁写正文前读 `genres/<体裁>.md`；用 XML 排版时读 `xml.md`。

## 一、判定原则（冲突时按序取舍）

1. **读者本位**：先回答「读者是谁、为什么读、带着什么任务来」。按读者的任务组织内容，不按功能或作者视角罗列。
2. **结构先行**：结论先行，先整体后局部。每节只回答一个问题；并列用列表、步骤用编号列表、二维映射用表格、因果/流程用图示。
3. **视觉服从语义**：先定全篇主线与每节中心命题，再让视觉层级复现内容优先级。文档脱离讲解仍完整可读。
4. **最低理解成本**：选最能降低理解、执行、出错成本的表达，而不是字符最少或制作成本最低的形式。
5. **克制且连贯**：每个视觉组件必须承担导航、比较、解释、证据或行动中的一项；去掉不影响读者任务的装饰。同类关系全文复用同一组件与样式。
6. **约束栈**：事实 > 用户硬约束 > 读者任务 > 内容 > 组件样式。格式不得反向改变内容判断。
7. **表达一致**：同一对象、动作、状态全文同名；标题层级与编号一套体系走到底——自动编号模式（`seq="auto"`，正文标题不手写序号）与中文手写模式（`一、→（一）→ 1.→（1）`）**二选一**，绝不出现「一、」下接「1.1」。

## 二、体裁选择（按读者任务选骨架）

下表选**且只选一个**；关键词仅用于召回，**排除信号优先于同名词**（如「报告 / 分析 / 摘要 / 正式」单独出现不定路由）。选完后读 `style_guide name="<体裁名>"` 取骨架与硬约束。

| 读者任务（关键词仅召回） | 体裁 |
|---|---|
| 快速知悉 / 决策封面 / 会前准备（备忘、简报、决策摘要） | `memo-brief` |
| 按周期判断相对承诺的位置（周报、日报、月报、项目状态） | `weekly-report` |
| 请具名决策者批准方向 / 预算 / 资源（提案、立项、资源申请） | `proposal` |
| 方向已定，把一次性项目 / 变更 / 活动转成可协同交付（项目计划、实施方案） | `execution-plan` |
| 定义用户问题、范围、产品行为与验收（PRD、用户故事、验收标准） | `prd` |
| 评审未来技术设计 / 查精确契约 / 调查未知故障（RFC、API、架构、事故调查） | `technical-doc` |
| 按已批准路径重复执行或预置响应（SOP、runbook、值班手册、处置预案） | `sop-tutorial` |
| 从已结束周期提炼证据化学习并改变下一轮（复盘、经验教训） | `retrospective` |
| 记录已发生会议的决定 / 异议 / 行动（会议纪要、行动项） | `meeting-minutes` |
| 回答明确研究问题，方法与样本决定可信度（调研、访谈、用户研究） | `research-report` |
| 解读已定义指标 / 趋势 / 分布（数据报告、经营数据、指标复盘） | `data-report` |
| 比较投资 / 资源 / 市场 / 产品选项，但**不要求批准**（商业分析、可行性、自建或采购） | `business-analysis` |
| 让专业读者系统理解并**评估**问题、框架或方案（白皮书、行业框架） | `white-paper` |
| 已授权的内部规则 / 安排、可复核的检查整改记录（制度、公司通知、讲话底稿） | `formal-doc` |
| 党政机关法定公文制发（明确要求公文 / 红头 / 套红 / 文号 / 主送） | `official-redhead` |

**消歧要点**

- 方向**未定**（在选方向、申请资源、形成授权入口）→ `proposal`；方向**已定**只是落地 → `execution-plan`；只是比较选项、不形成批准入口 → `business-analysis`。
- 一次性学习/教程 → `sop-tutorial` 也可；但它是学习内容而非重复执行路径时，归 `research-report` 或对应知识类体裁。
- 「正式」单独不触发 `formal-doc` / `official-redhead`；必须有法定文种、行文关系、文号、主送等制发要素才走 `official-redhead`。
- 渠道类体裁（邮件 / 微信公众号 / 小红书）暂未内置，需要时按 `style` 总则自行组织。

## 三、视觉策略（动笔前先定档）

- `formal`：正式、克制。不用 emoji、高亮块、彩色单元格，只保留正式体裁必需的结构（公文、法务、对外报告）。
- `normal`（默认）：按内容需要组件；只有能降低理解/执行/出错成本时才扩展视觉表达。
- `rich`：主动用表格、图示、分栏、图片、高亮块，但每个组件都要有明确目的，不设数量配额也不堆砌。

## 四、组件选择表（信息关系 → 表达）

| 信息关系 | 用什么 |
|---|---|
| 同组字段的精确比较或映射（参数、字段、方案对比、口径） | 表格（≥3 行 3 列才值得） |
| 流程、依赖、分支、时序、层级、因果、拓扑 | 图示（`<whiteboard type="mermaid">` 或图表围栏） |
| 对象、场景、界面、视觉证据 | 图片（独立成行 + 题注） |
| 两组简短、等权、适合横向阅读的信息 | 分栏（每栏 ≤ 3 行，不塞长文） |
| 单个关键提醒、限制、风险、前置条件 | 高亮块（配 emoji） |
| 可勾选的计划/清单/验收项 | 待办 |
| 简单并列、步骤、连续论述 | 列表或段落 |

**不要求每节都有组件**；正文为主、组件为辅，没有对应信息关系就不加。

## 五、颜色与 emoji

- 色相只用 `red orange yellow green blue purple gray`；正文保持中性，不整段染色。
- 高亮块背景：`light-*`（默认）用于提示，`medium-*` 仅用于强提醒；边框与文字色用基础色相（`medium-*` 边框不支持，会回落基础色）。
- 表头用默认浅灰；彩色单元格只表达状态或分类，不整表铺色。
- emoji 只在高亮块里表达语气（💡 提示 / ⚠️ 警告 / ✅ 完成 / 📌 前置 / 🚧 风险）；`formal` 档禁用。

## 六、排版规格（硬性）

- **标题**：文档标题由 title 承担；正文标题 h1→h2→h3 连续不跳级；每个标题下必须有正文，禁止连续堆标题；层级不超过 4 级，超过说明该拆文档。
- **编号**：`seq="auto"` 自动编号或中文手写，一套到底。
- **段落**：一段一个意思，3~5 行为宜；超过 6 行拆分或列表化。
- **列表**：并列用无序、步骤/优先级用有序；嵌套不超过 2 层。
- **表格**：给列宽（`<colgroup>`），避免默认等宽把内容挤成长条；首行表头；单元格不堆长段落。
- **代码与命令**：一律代码块 + 语言标识；必要时加 `caption` 说明用途；正文不混代码。
- **图片与图示**：独立成行、给题注；图示必须配文字等价说明，不把图当唯一证据。
- **分割线**：只用在大的章节切换处；一屏出现 3 条以上说明结构过碎。
- **引用**：仅用于原文摘录或他人观点。

## 七、工作流（两阶段：整篇成型 → 回查精修）

**阶段 1 · 成型（一次写完，不挤牙膏）**
1. 明确读者任务、体裁、硬约束（字数、格式、口径），读 `genres/<体裁>.md` 取骨架。
2. 定视觉计划（档位 + 用哪些组件），写在动笔之前。
3. 一次生成完整结构：标题骨架 + 每节正文 + 组件 + 证据；用 `import_xml` 一次落地（排版表达最全），内容极简、无需富排版时用 `import_markdown`。
4. 结构较大或含图片/图示时，**先跑 `import_xml` 的 `dry_run` 预检**：拿到块画像、图片可达性与图表渲染结果，按问题清单就地改，再正式导入（避免空文档与半成品）。

**阶段 2 · 精修（只做最小范围改动）**
5. 回查：大文档先用 `get_doc_blocks outline=true` 看大纲定位到节，再用 `get_doc_text`（传标题 `block_id` 只读该节）/ `find_blocks` 读具体内容。
6. 改一处措辞（可能多处命中）用 `replace_text`（先 `dry_run` 看命中），改整块用 `update_block`，增删块用 `add_blocks` / `delete_blocks`，表格过窄用 `set_table_width`。
7. 跑 `lint_doc` 体检，按问题清单逐条修。
8. 每轮写操作后重新回查，不沿用上一轮 block_id；已正确的内容不重写。

## 八、交付前自检

- [ ] 标题层级连续、每节有正文、无连续标题堆叠
- [ ] 编号体系唯一且全文一致
- [ ] 表格有表头、列宽合理、无长条单元格
- [ ] 代码块都有语言标识；命令/日志未混入正文
- [ ] 图片独立成行且有题注；图示有文字等价
- [ ] 高亮块只出现在真正需要提醒处，配色语义不超过 2 种
- [ ] 无占位符残留（TODO/xxx/待补）、无空块
- [ ] 结论在开头；只读标题也能看懂结构
