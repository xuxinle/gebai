# 相期子Agent

把 agent 的请求送到用户桌面上的**相期**常驻窗口，并把他怎么回带回来。

```
会话 A ─┐
会话 B ─┼─▶ 控制器（进程级单例，WS 服务端）◀──ws── 相期窗口（桌面）
会话 C ─┘         │
                  └─ card_notice / card_ask / card_authorize / card_list / card_dismiss
```

## 定位：内置域（`packages/agents/src/agents/xiangqi/`）

相期是**核心能力**而非二开扩展：它是歌白对外的第二个界面（桌面提醒面），
与网页、飞书群同级。所以它住在内置域，随歌白一起构建/发布，而不是放在
`custom/`（那层是「不碰上游、可整体迁移」的客制层）。

对宿主内代码的含意：需要直接推卡的地方（如拟人模式推授权卡）**不经源码 import**，
而是取子Agent 定义上的工具（`subAgents.defOf("xiangqi")` —— 与模型 `agent_load`
同一来源）——内置子Agent 是构建期打包的，源码路径不属于 server 的可引用面。

## 五个工具

| 工具 | 阻塞 | 用途 |
|---|---|---|
| `card_notice` | 否 | 纯告知 |
| `card_ask` | 是（可超时） | 需要用户定夺（choice/todo） |
| `card_authorize` | 否 | **送用户去浏览器办事**（授权/登录）——带链接，完成后主动撤卡 |
| `card_list` | 否 | 看谁还在等 |
| `card_dismiss` | 否 | 传 `id` 只撤那张；不传清全部 |

### 为何 `card_authorize` 不复用 `card_ask`

| | `card_ask` | `card_authorize` |
|---|---|---|
| 用户要做的 | 在卡片上选一个 | **离开去浏览器完成** |
| 答案从哪来 | 卡片上的点击 | 外部系统回调（不是卡片） |
| 阻塞姿态 | 等答复（可超时） | **不阻塞** |
| 完成后 | 用户点选 → 返回 | 外部状态变了 → **调用方主动撤卡** |

硬塞进 `card_ask` 会让「阻塞等待」这个语义失真——授权完成不会有 `answer` 回来。

## 为什么是子Agent，不是全局工具

相期一共四个工具。做成全局工具的话，它们会进**每一个**会话的系统提示——
而实际会用到相期的会话可能不到 5%（多数后端任务根本不需要弹窗给人）。

这是一笔持续性的上下文税。子Agent 只在装载时付一次，还能带上「什么时候该
打扰用户」的判断准则——那部分很难塞进工具 description。

## 为什么不能做成 `subsession_run` 子会话

弹一张卡片要起一个独立 LLM 循环？那是荒谬的。相期是**外设**（显示面），
不是任务执行者。它是能力模块（`agent_load` 装载，工具并入当前工具集）。

## 方向：控制器是服务端，相期是客户端

```
相期（桌面窗口）──ws://host:port/xiangqi──▶ 控制器（跑在 gebai 宿主里）
                ◀── {"type":"cards","cards":[…]}     下发卡片（权威列表，整批替换）
                ──▶ {"type":"answer","id","kind",…}   用户答复
```

这个方向由相期那边定（`shuangtian/examples/xiangqi` 用自研 WS 客户端连出去）。

⚠ **把方向搞反的后果很隐蔽**：控制器去主动连 `url` 会连到自己的服务端形成自环——
`isConnected()` 报 true、`send()` 不报错，但卡片永远到不了窗口。
实测踩过：`#cards` 一直是空的，而所有日志都在说"发送成功"。

## 连接为什么必须是进程级单例

相期是常驻窗口。如果连接跟着会话走：

1. 会话一结束连接就断，窗口变孤儿
2. 多个会话各自监听 → 抢同一个端口，或抢同一个窗口，卡片互相覆盖

所以控制器是**进程级单例**（`controller()`），工具只往它上面投递。
端口只能 bind 一次，窗口也只有一个——这是「不抢窗口」的全部机制。

## 四个工具

| 工具 | 阻塞 | 什么时候用 |
|---|---|---|
| `card_notice` | 否 | 办完了说一声、有变化值得知道但不需要他动手 |
| `card_ask` | 是 | 需要他定夺（`choice`）或需要他动手（`todo`） |
| `card_list` | 否 | 看还有谁在等 |
| `card_dismiss` | 否 | 这批都过时了 |

**按阻塞语义分，不按 kind 分。** 三个 kind × (投递/等待/查询/撤回) 会膨胀成
十几个工具，而参数形状几乎一样。工具数量本身就是上下文税。

`card_ask` 的阻塞语义与引擎既有的 `ask` 工具**一致**——两者都是"在等用户输入"，
不该有两套等待行为。

## 两条关键语义

### 1. 送不到要如实说，但不抛错

未连接时 `push` 仍收下卡片（进 `live`，连上会重推），但返回 `delivered: false`。

- **不抛错**：抛错会让调用方重试 → 同一件事推两张卡，用户回来看到两条一模一样的
- **不假装成功**：静默成功会让模型以为用户看到了，于是它继续跑，而提醒根本没送到

工具把 `delivered=false` 写进给模型的文本（"**用户看不到**"），而不是抛异常。

### 2. 超时 ≠ 失败

`card_ask` 默认等 5 分钟（上限 30 分钟）。超时返回的话必须说明**卡片还在窗口上**：

> 等 300 秒没有收到答复。⚠ 卡片**仍留在用户窗口上**，他随时可能处理。

这是字面意思：相期除了经 WS 回 `answer`，还会把答复落 `outbox/<id>.json`。
即使 WS 断在答复那一刻，答复也不会丢。

所以超时后**不要重试**（那会推第二张卡），而是先做不依赖这个决定的部分，
或者明确告诉用户"我在等 X 的决定"。

## 审批

四个工具全部免审批。

理由：它们的操作是**把信息送到用户眼前**，不修改任何东西。加审批会变成
「为了提醒用户，先要用户批准提醒」——荒谬，而且会卡住无人值守场景
（那时恰恰最需要把问题推给人）。

`card_ask` 本身就是一次「请用户定夺」，天然带人工介入点。

## 验证

```bash
# 单元测试（用真 WS 客户端冒充相期）
bun test custom/agents/xiangqi

# 端到端（真启动相期进程、真点击、真答复）
bun run custom/agents/xiangqi/e2e.ts <xiangqi.exe 路径>
```

e2e 覆盖：连上 → notice 渲染（轻提示或主界面）→ choice 按钮出现 →
真点击 → 答复经 WS 回控制器 → dismissAll 清空 → **断掉 WS 后再点一次**
（验 outbox 兼底真的接得住）→ 进程存活。

## 文件通路：两条降级路

WS 是主路，但报障时它是单点。相期本来就设计了两条文件降级路，控制器都接上了：

| 方向 | 主路 | 降级路 |
|---|---|---|
| 推卡 | WS `{type:cards}` | 写 `inbox/<id>.json` |
| 答复 | WS `{type:answer}` | 读 `outbox/<id>.json`（轮询） |

**推卡降级只在未连接时走**——WS 通了就以 WS 为准（整批替换）。两路同时送
会让同一张卡在窗口上出现两次（文件是追加语义，不知道整批）。

**答复兼底是轮询的**（缺省 500ms）。相期**总是**写 outbox（不只 WS 失败时），
所以“超时不丢答复”不是口号。三个细节都有测试钉住：

- **答复先到、后来才等**：存进 `arrivedEarly` 缓存，`waitForAnswer` 先查它，
  不白等满整个超时
- **陈旧文件不乱投**：不在 `live`/`waiting`/`arrivedEarly` 里的 id 一律忽略
  （可能是上个进程留下的）
- **坏文件不被标记已消费**：刚好读到半写状态时不永久丢件，下轮再看

目录位置用 `XIANGQI_HOME` 配（缺省 `<cwd>/相期`，与相期自己的
`resolve_home()` 一致）。**必须与相期启动时的 `--home` 是同一个**。
