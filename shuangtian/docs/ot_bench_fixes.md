# 把片子从「指标不达标」救回来：实测规律

> 来源：2026-10-24 对标 onetake 13 个 case，逐个修到 PASS 的过程。
> 每条都带实测数字，不是推测。

## 零、先分清三种「静止」

ppl 说「静止占比高」时，实际是三种完全不同的病，修法相反：

| 类型 | 判据 | 实测特征 | 修法 |
|---|---|---|---|
| **A. 逐帧完全相同** | 帧差 = **0.00** | `mean=0.00, still=100%` | 画面里真没东西在变（只有一个不动的元素） |
| **B. 有动但太小** | 帧差 0.1~1.0 | `mean=0.2, still=100%` | 元素太小 / 参照物不够大 |
| **C. 相机/元素恒定** | 帧差 0.05~0.5 | 关键帧之间存在长平台 | 去掉平台，让它持续动 |

**判法**：逐秒算帧差，看 `mean` 的绝对值。

- `mean = 0.00` → A 类，去找"为什么一帧都不变"
- `mean ∈ (0, 1.2)` → B 类，量元素尺寸
- `mean ∈ (1.2, 3)` 但 still 高 → C 类，找关键帧平台

逐秒数据的脚本（复用评测口径，32×18 网格）：

```python
out = subprocess.run(["ffmpeg","-v","error","-i",frames+"/frame_%05d.png",
                      "-vf","scale=32:18,format=gray","-f","rawvideo","-"], capture_output=True)
raw = out.stdout; W,H=32,18
sec={}; prev=None
for i in range(len(raw)//(W*H)):
    cur = raw[i*W*H:(i+1)*W*H]
    if prev is not None:
        d = sum(abs(cur[k]-prev[k]) for k in range(W*H))/float(W*H)
        sec.setdefault(int((i-1)/30.0), []).append(d)
    prev = cur
```

## 一、A 类：画面里只有一个不动的元素

**实例（c06-pith，1–5 秒）**：`mean=0.00`、`still=100%`。
抽帧才看出：画面是一根放大的光标，**从 1.55 到 1.90 位置固定、字还没开始打**。

**教训**：相机关键帧改得再勤也没用——**画面里没有东西可动**。
先抽帧看"这一秒画面上到底有什么"，再决定改相机还是改元素。

**修法**：让那个元素自己动（滑入 / 打字 / 呼吸），并且**位移要跨格**（≥60px）。

## 二、B 类：元素太小，格均值测不到

这是最贵的一条，**量化之后一目了然**。

评测网格 32×18（一格 60×60px），静止阈值 1.2（0~255 尺度）。

一个直径 `d` 的圆点在一格里占 `(d/60)²` 的面积；
相机平移 `s` 像素时，格均值变化大致正比于「边缘扫过的面积」：

```
Δ ≈ 2·d·s / 3600
```

**实测三档（c02-onedot，同一份脚本只改背景点阵）**：

| 点阵直径 | 间距 | 不透明度 | p95 | 静止占比 |
|---|---|---|---|---|
| 2.6（原片尺寸） | 48 | 0.55 | 1.63 | 90.9% |
| **14** | 60 | 0.85 | **3.22** | **54.6%** |
| 13 | 72 | 0.32 | 1.74 | 83.1% |
| 13 | 72 | 0.62 | **2.29** | **76.8%** |

**判读**：

- `d=2.6` 时 Δ ≈ 2·2.6·160/3600 ≈ **0.23** —— 远低于 1.2，永远测不到。
- `d=14` 时 Δ ≈ 1.24 —— 刚过阈值。
- 不透明度从 0.85 降到 0.32，Δ 直接掉回不合格（对比度也是因子）。

**所以「让画面活着」不是加噪点，是加"足够大的可测参照物"。**

## 三、C 类：关键帧平台

`keys()` 在两端值相同时**输出恒定**，而"相机站定"就是"画面站定"。

**实测（多个 case 同一形态）**：

| case | 平台 | 时长占比 | 修法 | 效果 |
|---|---|---|---|---|
| c05-clearing | `dayH` 26→26 (9.75–15.0) | 35% | 改成 26→58 | 74.8% → 76.8%（**几乎没用**） |
| c07-launch | zoom 恒 1（0–4.4） | 15% | 叠 0.09 rad/s 慢漂移 | 63.0% → **58.4%** |
| c06-pith | zoom 0.52→0.52 (18.4–21.5) | 14% | 每个关键帧给不同值 | 见后 |
| c12-domino | 双正弦 ±3° | 全片 | 提到 ±5°，全局加强 | 40.2% → **27.2%** |

**注意第一行**：c05 改 dayH 几乎没用——因为 `dayH` 经 `zoomIn = (dayH-24)/1536` 归一化后，
26→58 只让 `grow` 从 1.00 到 1.05。**改参数前要先算它经过几层映射**。

真正的修法是**直接在 `grow` 上叠加时间驱动的放大与平移**：

```js
const tailK = clamp((t - 9.75) / 5.25);
const tailGrow = 1 + tailK * 2.4;                  // 真正放大
const tailShiftX = tailK * (sin(t*0.55)*220 + t*42); // 持续平移（跨格）
```

效果：静止 74.8% → **48.6%**，中位数 0.152 → **0.778**（参考 0.511，已超）。

## 四、背景纹理的三种放法，只有一种对

c02 的 lattice 试了三次（每次都抽帧确认）：

| 放法 | 结果 | 为什么 |
|---|---|---|
| 相机变换**之前** | p95 3.22 ✅ | 点阵随相机移动 → 整屏纹理在动 |
| 相机变换**之后**（屏幕空间固定） | p95 1.61 ❌ | 相机推拉时纹丝不动，格均值不变 |
| 之后 + 视差偏移 | p95 1.62 ❌ | 取模回绕让位移抵消回原位 |

**结论**：要"给相机提供可测参照"，纹理必须**跟着相机走**。
代价：推镜时点阵会被一起放大（观感像坐标纸）——用低不透明度 + 让开文字区缓解。

## 五、文字是图层、会在 shapes 之下

`paint_layers` 在 `paint_script_shapes` **之前**。所以：

- 用图层画字 + 用 shapes 铺背景 → **字完全看不见**（c08/c09/c10/c12 都撞到）
- 已用图层画字的片子加背景，必须**让开文字所在的横向带**：

```js
const inTextBand = (gy > 230 && gy < 320) || (gy > 480 && gy < 570);
if (inTextBand) continue;
```

## 六、工作纪律（都是时间换来的）

1. **先抽帧再改**。c06 我改了三轮相机才发现"1–5 秒画面上只有一个不动的光标"。
2. **逐秒数据优先于单项指标**。`still_ratio` 一个数会掩盖"哪几秒在静"。
3. **改完先 node --check**。JS 语法错会让渲染器**静默降级为纯 JSON**，画面只剩背景而无报错。
4. **量一下你的改动经过几层映射**再报"应该有用"。
5. **一次只改一类东西**（相机 / 元素 / 背景），否则不知道是哪一项起作用。
6. 改完**必须抽帧看**——指标过而画面坏（c02 第一版点阵压字）是真实存在的失败模式。

## 七、最贵的一条：layout 抛错会被**静默降级**

裁云的 layout 按设计"脚本抛错 → 降级为纯 JSON，导出继续"。这在生产上是
正确的（一条片子不会因为一个动效写错就出不来），但对**排查是灾难**：

> 出片成功、报告有数字、指标能算 —— 而画面只剩背景，**没有任何报错**。

### 实测代价

`c06-pith` 的 `keys()` 里调用 `ease(...)`，而那是我一度误以为缺失的符号。
实际上 `ease` 是**裁云的宿主函数**（`layout.cpp` 的 `register_function` 白名单），
由引擎注入。我在脚本里又声明了一个同名函数，于是 `Identifier 'ease' has already
been declared` —— **整份 layout 加载失败**，每帧降级。

而我在改什么？相机关键帧、光标滑动、缩放曲线。**全都进不去**。
逐秒数据一直是 `mean=0.00`（这是降级的特征），我却以为是"元素太小"。

### 判据：`mean` 恰好等于 0.00 就是降级

| `mean` | 含义 |
|---|---|
| **0.00**（精确） | 极可能**降级**：layout 没产出，画面是纯背景 |
| 0.01~0.5 | 有产出但元素太小 / 参照物不够 |
| 0.5~1.2 | 接近阈值，差一点 |
| > 1.2 | 这一秒是"在动"的 |

"精确 0.00"和"0.03"是两种完全不同的病——前者先查 layout 有没有抛错。

### 工具：`scripts/check_layout.py`

渲染**之前**把 layout 逐帧跑一遍（10 秒的事）：

```bash
py scripts/check_layout.py out/otbench/c06-pith/pith.js --duration 21.5
py scripts/check_layout.py --scan out/otbench        # 扫全部 case
```

它注入**与宿主白名单一致的桩**（`ease` / `spring` / `settle` / `lerp` / `clamp` /
`snap` / `rand`）。**没有这层注入就会得到一堆假警报**——实测第一版
把 13 个本来健康的 case 全报成 "ease is not defined"。

`ot_bench.py` 已把它接成**渲染前门禁**：检查不过直接退出，不出片。

## 十、p95 上不去，先查**内容密度**（不是运动幅度）

`c06-pith` 的对标过程把这条暴露得很清楚：

| 指标 | 本片 | 参考片 | 判定 |
|---|---|---|---|
| 静止占比 | **41.1%** | 54.0% | 优于参考 |
| 变化中位数 | 0.601 | 0.856 | 0.70×（过门槛 0.3×） |
| **变化 p95** | **4.54** | **11.01** | **0.41×（门槛 0.5×，不过）** |

**静止占比与中位数都过了，只有 p95 不过。** 这排除了"整体太平"，
指向"高运动帧的强度不够/数量太少"。

### 试过但无效的做法

| 做法 | p95 变化 |
|---|---|
| 背景纹理（页面坐标，被尺寸上限挡掉） | 4.673 → 4.733（噪声级） |
| 背景纹理（屏幕空间，flow 1450） | 4.733 → 4.647（**反而降**） |
| 相机推拉关键帧去平台 | 4.892 → 4.673（噪声级） |
| 光标滑入 + 提前打字 | 4.673 → 4.647（噪声级）|

**结论：p95 不由"背景/相机"决定。** 它们是"整屏平缓变化"，拉的是静止占比与中位数。

### 真正的原因：抽帧对比

参考片这一段是**工具调用清单**：

```
▪ grep  "--bg-base" -r src                    7 hits
▪ read  src/styles/globals.css              142 lines
▪ find  src -name "SettingsPanel*"            1 file
▪ edit  src/styles/globals.css                +18 -2
▪ bash  npm run build                           1.2s
```

每行 **4 个元素**（彩色图标 / 工具名 / 参数 / 右对齐数值），26 行 ≈ 104 个图元。

我的版本是**纯左对齐文字**，一行一个文字图元，只占左半屏。

**同样的运动幅度，图元多 4 倍 → 变化的格子多 4 倍 → p95 高 4 倍。**

### 判据：p95 抓的是**少数极强跳变**，不是"平均动得多"

把参考片逐秒的 **max** 打出来，真因就清楚了：

```
参考片 pith-21s 逐秒：
 1s mean= 7.42 max= 98.20   <<< 整屏放大到一格的像素格
 7s mean= 8.68 max=208.47   <<< 主题瞬间翻转（深色→浅色）
12s mean= 6.51 max= 22.91
其余秒            max < 7
```

它的 p95（11.01）**全部来自这三次极强跳变**。抽帧看 1.3s 是"整屏被单个字符格铺满"——
一帧之内整屏换色。

所以 p95 低的正确问法是：

> **这一片里有几次"整屏换内容"的跳变？**

而不是"平均动得够不够"。四轮改动（背景纹理 / 相机去平台 / 光标滑入 / 内容密度）
把 p95 锁在 4.5~4.9，就是因为它们都在做"平缓变化"，而 p95 要的是"陡变"。

实现上对应两类手法：

| 手法 | 例 |
|---|---|
| **极端尺度跳变** | zoom 3000 → 440（0.45s 内），整屏从"一片暗"变成"满屏格子" |
| **整屏属性翻转** | 主题深→浅、反色、遮罩闭合，一帧到位不做渐变 |

这与"硬切要卡在拍上"同源：**陡变是有意的，别用渐变抹平它**。

### 附：元素数量仍是必要而非充分

增加每行的元素数（1 个 → 4 个）能提高"变化的格子数"，但没有陡变时
p95 只从 4.54 到 4.73。**密度抬高基线，跳变抬高 p95。**

### 附带的两条增强（都在高运动帧上生效）

1. **逐行点亮**：每行的图标从暗到亮是一次跳变，比整体平移的帧差大得多
2. **扫过的高亮条**：当前"正在处理"的行有一层底色，每帧位置不同

这两条的成本几乎为零，但都是"高对比、局部、逐帧变化"，正是 p95 抓的东西。

### 「改了参数，数字一字不变」的三个原因（按命中率排）

**这是本轮踩得最多的一条（两次）。** 每次都是在调参，而调参没生效。

| # | 原因 | 判据 | 处理 |
|---|---|---|---|
| ① | **帧缓存**：`out/<case>/frames/` 里是上一轮的 PNG，渲染器复用了 | `film.mp4` 的 mtime 变了但数字完全不变 | 删 `frames/` 与 `film.mp4` 后重跑 |
| ② | **layout 抛错降级**：画面只剩背景 | 逐秒 `mean` **精确 = 0.00** | `check_layout.py` |
| ③ | **参数经过几层映射** | 改了 A 但画面只由 B 决定 | 读一遍 A 被谁用、换算几层 |

实测两次：
- `c05-clearing`：把 `dayH` 26→58，数字 74.8→76.8（几乎不动）——
  因为要先经 `zoomIn = (dayH-24)/1536` 归一化，实际只放大 5%
- `c06-pith`：加极端 zoom 跳变（3000→440）后数字**一字不变** —— 是帧缓存

**操作纪律**：改完 layout 先删 `frames/`，再渲染。这条成本 1 秒，能省一轮 5 分钟。

## 十一、性能优化会打断评测链路（实测，代价三条片子同时误判）

### 现象

把裁云导出默认改成**管道直送 ffmpeg**（不落 PNG，为提速）之后，
重跑三条片子，**全部报 `density` 不达标**：

```
c12-domino    静止 22.8%  change_median=None  change_p95=None
c05-clearing  静止 46.1%  change_median=None  change_p95=None
c09-skilldemo 静止 94.0%  change_median=None  change_p95=None
```

静止占比与变化密度都跟改前一致（clearing 一直是 46.1%），**片子完全正常**。

### 真因

评测的所有运动指标都是从 **PNG 帧序列**量的：
`motion_qa --dir out/<case>/frames`。

而管道模式不落 PNG → `frames/` 是空目录 → motion_qa 报
`[片子] 无法测量：帧数不足（0）` → `change_median` / `change_p95` 解析成 `None`。

### 为什么误判成 `density`

旧代码只判断 `median < ref_median * 0.3`，而 `None` 经 `.get()` 与比较后
被当成 0.0 → 报"中位数 0.0 < 参考的 0.3×"→ `density` 不达标。

**错误信息（中位数太小）与真因（根本没量到）差了整整一层**，
而 hint 还指导去"加元素尺寸/数量"——那是纯粹的误导。

### 两处修正

1. **`ot_bench.py` 显式传 `--keep-frames`**：评测依赖帧序列，
   就必须为评测保留它，不能跟随产品默认值。
2. **指标缺失改为独立判决**：`change_median` / `change_p95` 任一为 `None`
   就报 `measurement` 并直接返回，**不再落到任何内容类判据上**。

### 可推广的判据

> **派生指标的缺失必须与"指标值不达标"分开报**。
> 前者是"没测到"，后者是"测到了但不行"——把两者混在一起，
> 会让排查方向完全跑偏（这次差点去改三条片子的构图）。

> **改了产物的生成方式，要重跑一次依赖该产物的验证**。
> 提速改的是导出路径，而被影响的是评测路径——两者共用 `frames/` 这个隐式契约。
