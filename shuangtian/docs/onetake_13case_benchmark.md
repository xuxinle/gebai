# 裁云 × onetake：13 条示例逐条对标（结果）

> onetake 的 11 条公开成片（13 个 case 目录）**全部用裁云做了一遍**。
> 13 条脚本 + 13 个 mp4 + 13 份指标 JSON 在 `out/otbench/`，随时可复算。

## 零、先说结论：本轮最大的产出不是片子，是**发现尺子错了三次**

13 条片子本身证明的是“能不能做”。而真正影响了能力的是：同一形态的缺陷（**尺子失效
时静默通过**）在一轮内出现了三次，其中两次是子会话独立撞到的。

| # | 形态 | 后果 | 状态 |
|---|---|---|---|
| 1 | 并行渲染静止占比**分母恒为 0** | 报「静止 0.0%（0 对）」而摘要无异常 | 已修 + C++ 回归测试 + 逆向验证 |
| 2 | 用变化**峰值**当强度 | motion-web 峰值 234 来自一帧硬切黑场，同片 p95 只有 2.01 | 改用 p95 |
| 3 | 相对判据缺参考值时**静默跳过** | `violations` 为空 ⇒ 退出码 0 ⇒ 看上去 PASS，实际一条判据没跑 | 已修（`incomplete`/`undecided` + 退出码 4） |

第 3 类最贵：它不会让结果变难看，只会让结果**看起来正常**。具体两笔账：

- `ref_baseline.json` 里**从未有过 `bright_ratio` 字段** ⇒ 「过亮」这条判据对 13 条片子**一次都没生效过**；
- 不传 `--ref-baseline` 时所有相对判据都不执行 ⇒ `violations` 为空 ⇒ 脚本返回 **0（PASS）**。

而「过亮用绝对阈值」本身也是错的：参考片里 knockon / overlap / clawd 是 **100%**、
ebb 96.2%、motion-web 95.3%——它们是亮调片，按绝对红线全部该判红。

护栏：`scripts/test_ot_bench_judge.py`（14 条）+ `scripts/verify_judge_reverse.py`
（逐条回退→确认变红→恢复，4 条全拦住）。

## 二、5 条的差距是什么（逐条归因，不是「再调调」）

| case | 缺口 | 真因 |
|---|---|---|
| one-dot | p95 1.64 vs 3.78 | 参考片峰值 27.07 来自**633 px/帧的单帧位移**（它开头 440× 抢拍）。我们没有"一帧换掉整屏"的镜头语言。 |
| clearing | p95 6.5 vs 16.5、密度 0.15 vs 0.51 | 参考片钻到 **300×**（两次连续钻），我们最多 3050/1440 ≈ 2.1×（受 G1/G2 限制，见第三节）。倍率不够 = 整屏变化量不够。 |
| pith | 静止 81.7 vs 54.0 | 数据流段（3.3–6.3s）24 行文字每 0.115s 才出一行；参考片是 24 行**连续滚**。 |
| launch | 静止 63.0 vs 47.9 | 三条片子的"桌面"段落仍是静止的（参考片有 dolly 全程在走）。 |
| domino | 静止 36.5 vs 17.2、密度 3.09 vs 8.28 | 阵列已经很密（12,346 台），但“前一代→后一代”的过渡帧有整秒静止。 |

**共同点**：卡在「p95」的片子只有 3 条，而它们都指向同一个能力缺口——
**“整屏同时变”的手段只有三种**：全屏像素阵列（launch 的 LED 屏，p95 35.2）、
大幅拉远（unbroken 6.5×）、密集小图元（domino 12,346 台手机，p95 50.9）。
三种都用上了，能过的就过了。**剩下的差距是“没有第四种手段”，不是“调得不够”。**

### 一条被两个子会话独立验证的硬规律

clawd 子会话付了 6 轮代价把它按实了（overlap / infra / domino 同规律）：

| 底层纹理 | p95 | 静止 |
|---|---|---|
| 纯色（0 纹理） | 0.93 | 95.1% |
| 棋盘格，线宽 1.6px | 2.55 | 83.7% |
| 改成 100px 级**填充块** | 4.52 | 63.1% |
| 再加镜头三重运动 | 5.82 | 48.9% |
| 加对比与幅度 + 镜头守在内容附近 | 5.56 | 30.2% |

**关键：前四轮以为是“动效不够”，实际一直是“纹理没覆盖到格子”**——
60px 的格里，1.6px 的线只占 2.7% 面积，格均值几乎不动。
**任何“整屏都在动”的效果，先要把底层铺满能跨格的东西，再谈运动幅度。**

### 另一个陷阱：指标好但画面错

clawd 有一版 `followX` 扫到 980，而窗口在世界 x≈330–470——窗口被推出屏幕左侧，
抽帧只剩标题栏尾巴，**而指标很好看**（全屏桌面在滑）。
**桌面永远能靠滑动刷出高 p95，而主体已经不在画面里。** 所以 stills 必须逐张看。

## 三、必须修的框架缺口（这轮挡住的）

### G1 · 没有局部坐标系
`shapes` 全是绝对坐标。想在"一个格子里"画东西，必须手写 `pageOrigin/anchor` 换算。
代价：clearing 第一版把锚点当左上角，`dayH=2900` 时画面里只剩左下角一块会议条。
**方向**：给 `custom` 场景加 `pivot` + 局部 `scale`，子图元按局部坐标画。

### G2 · 相机缩放有硬上限
内容必须装得进画面，否则锚点之外全被裁掉。clearing 想钻 5200×，但页宽 900 ⇒
上限 1920/900 ≈ 2.13×。**这是 clearing p95 只有 6.5 的直接原因**（参考片钻到 300×）。

### G3 · 文字不能安全缩放
`LayerDelta.scale` 不重算 `align`。unbroken 字标 `scale 4.2→1` 后左半横到画面中偏、
右半还在原位。
**方向**：让 scale 以对齐点为原点，或提供 `pivot`。

### G4 · `caiyun_verify` 工具不可用
调用报 `registry?.has is not a function`。已把等价判据搬进 `scripts/ot_bench.py` 的
`judge()`（不再依赖它），但工具本身需修。

### G6 · `ScriptShape.rotate` 字段存在但绘制不使用（**已修**）
`schema` 能看到 `rotate`、解析也过了，但 `paint_script_shapes` 里没有 rotate 分支。
**比缺字段更贵**：schema 自省让人以为能用。两个子会话独立撞到（倾斜元素只能靠错位矩形近似，像梯子）。

**已修**：矩形/文字/多边形三类图元绕**包围盒中心**旋转；几何提到 `fx.cpp`
（`rotate_point_deg` / `rotate_points_about_bounds`）以便单测。
回归测试 6 条，逆向验证 4 条全拦住。

### G7 · 缺多边形填充图元（**已修**）
`shapes` 以前只有 圆/矩形/线/文字。凡需透视或倾斜的图元（三维近似、斜放卡片、投影阴影）
都只能用多个轴对齐矩形拼。

**已修**：`kind=4 多边形`，`points` 接受扁平数组或 `[[x,y],…]`；少于 3 个顶点不画。
遗留：旋转多边形**不支持圆角**（走 `fill_path` 而非 `fill_rect`）。

### G8 · `layout` 运行期错误静默降级，日志无痕迹（**未修**）
`layout.js` 抛 `ReferenceError` 时渲染器降级为纯 JSON（只画图层）——画面只剩背景，**日志一个字不打**。
两个子会话各自撞到（overlap 删了一行 `const push`、clawd 同类），都是靠抽帧发现画面空了才定位。
**与 G1–G3 同一形态：失败时静默。**

## 二·五、本轮修的能力（可直接用）

| 能力 | 用法 | 验证 |
|---|---|---|
| `kind=4 多边形` | `{kind:4, points:[x0,y0,x1,y1,…], color, rotate?}` | `fx_*.cpp` 6 条回归 |
| `rotate` 生效 | 矩形/文字/多边形均可，度、顺时针、绕包围盒中心 | 同上 + 逆向验证 4/4 |
| 设计像素→物理像素换算 | `painter.width() / kDesignWidth`（**不是** `p.scale()`） | 待补多分辨率回归 |

### G5 · 细线在验收网格里测不到
60px 格里 6px 细线只覆盖 10%。实测同一片只改笔触宽度（6 → 54px）：
p95 1.07 → 1.60、峰值帧 1.45 → 11.9。**这是方法论，不是缺陷**，已写进第五节。

## 四、已当场修的框架缺陷

### 并行渲染时「静止占比」恒为 0

| 项 | 内容 |
|---|---|
| 现象 | 16 路并行按 `fetch_add` 抢帧号 ⇒ 相邻帧永在不同 worker；帧差只在同一路内算 ⇒ 分母恒为 0。报「静止 0.0%（帧差 <1.2，**0 对**）」，摘要毫无异常 |
| 危害 | 这是对标头号指标。它恒为 0 会让每条片子看起来都"完全在动" |
| 修法 | 每帧的降采样灰度图留到归并后，按帧号排序再对相邻帧算差；新增 `frame_pairs` 字段，分母为 0 时摘要明写「⚠ 无有效相邻帧对：静止占比不可信」 |
| 验证 | 配 2 条回归测试 + **逆向验证**（回退修复 → 3 条变红 → 恢复 → 14 passed） |

## 五、这一轮学到的三条（可复用）

1. **「让画面动起来」的正确做法不是加微动，是加覆盖面积。**
   1~2px 的呼吸在 32×18 网格里完全测不到。实测同一片只改笔触宽度（6 → 54px），
   p95 从 1.07 到 1.60、峰值帧从 1.45 到 11.9。
2. **强度峰值来自「整屏都在变」的那一瞬，不是元素在动。**
   只有三种手段能撑住：大幅拉远（6.5×）、大面积扫描（全屏 LED 屏）、密集小图元。
   launch 把海报从 1080×700 的卡片改成全屏后，p95 从 4.3 到 35.2（8 倍）。
3. **量尺先自检。** 这轮三次误判全部来自尺子而不是片子：
   ① 直接引用参考片 README 的「静止 29.1%」——用我们的口径量是 **89.3%**；
   ② 用「变化峰值」当强度——motion-web 的 234 来自**第 859 帧一次硬切黑场**，同片 p95 只有 2.01；
   ③ 拿旧二进制出的轨迹判 carry——得到 0 carried，重编后同一脚本 0.90 PASS。
   现在 `ot_bench.py` 会先校验二进制比源码新，否则**拒绝出数**。

## 六、产物与复算

```
out/otbench/
  ref_baseline.json          # 13 条参考片的同口径基准
  summary_13.json            # 13 条成片的全指标汇总
  _ref/<case>/frames/        # 参考片抽帧（320×180，motion_qa 用）
  c01-unbroken/ … c13-clawd/
    <name>.json / <name>.js  # 导演脚本 + JS 编排层（片子在这里）
    film.mp4                 # 成片 1080p30
    frames/ trajectory.tsv   # 逐帧 PNG（指标来源）+ 元素轨迹（carry_qa 用）
    stills/ report.json      # 抽帧 + 全部指标与判据
    NOTES.md                 # 每片的结论
```

```bash
py scripts/ot_bench_ref.py                       # 重建参考基准（从帧目录，不重抽）
py scripts/test_ot_bench_judge.py                # 判据自完整性（14 条）
py scripts/verify_judge_reverse.py               # 逆向验证：逐条回退确认测试会红
py scripts/ot_bench.py --script out/otbench/c01-unbroken/unbroken.json \
   --out out/otbench/c01-unbroken --track-elements --motion-blur 4 \
   --ref-baseline unbroken-15s                   # 出片 + 四项验收一次跑完
```

退出码：`0` 通过 · `3` 有违规 · `4` **未判定**（相对判据没执行——不是通过）。

## 七、新工具（这轮为对标做的）

| 工具 | 作用 |
|---|---|
| `scripts/ot_bench.py` | 一条命令：出片 → 抽帧 → carry_qa → motion_qa → 与参考基准对比 → 判据清单。**先校验二进制新鲜度**，过期拒绝出数 |
| `scripts/ot_bench_ref.py` | 为所有参考片建同口径基准（抽 320×180 帧 + motion_qa），写 `ref_baseline.json` |

两者都带口径注释：为什么用 p95 不用峰值、为什么参考片要现场量、
为什么抽 320×180 不损失格均值。
