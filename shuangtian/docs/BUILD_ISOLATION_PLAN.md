# 构建隔离方案（独立构建目录 / 构建锁）——**只分析，未落地**

> **契约：方案（未落地）**。本文件回答"同一棵树上的多个构建进程为什么会互踩、
> 该加什么机制、代价多少"，**不是现状说明**。当前 `st` 既没有 `--build-dir`，
> 也没有构建锁；约束与判据见 `CONVENTIONS.md` §9.0④。
> 公共接口变更（`BuildOptions` 新字段、`st build/test` 新开关）按 §9 流程须先审阅本方案。

## 0. 事实清单（每条都能按行号核对）

| # | 事实 | 出处 |
|---|---|---|
| F1 | 对象临时名是 `unit->object + ".tmp"`：**固定名、不含 PID**，两进程抢同一个 `.tmp` | `src/pkg/build.cpp:1123-1124`，rename 在 `1180`/`1185` |
| F2 | 构建目录是 `fs::join(root, "build/<档>/obj")`，共 **5 处**各自拼一遍（build 的 obj/bin、run_tests 的 obj/bin、PCH 的 build_dir） | `src/pkg/build.cpp:935-937`、`1818-1820`、`2281-2283` |
| F3 | 构建期嵌入目录也是独立拼的 `build/<subdir>/embed/<scope>` | `src/pkg/embed.cpp:185-186`；`include/st/pkg/embed.hpp:50` 的 `build_subdir` 是**子目录名**，不含 `build/` 前缀（`22` 的注释写明了完整形状） |
| F4 | PCH 与链接产物**直接 `-o` 覆写到最终路径**，不过 `.tmp`（原子写只覆盖编译出的 `.o`） | `src/pkg/build.cpp:573-574`（gch）、`1406-1407`（链接） |
| F5 | 共享对象缓存 store/restore 走 `fs::copy_file`（overwrite），**非原子 rename** | 读侧 `src/pkg/build.cpp:347-348`；写侧 `378-379`；目录 `286-299` |
| F6 | 缓存键含**源绝对路径**（不含构建目录）；PCH 身份 token（`<pch:mtime:size>`）会入键 | `src/pkg/build.cpp:1013`（源路径）、`524`/`1016`（token） |
| F7 | `st init` 从**可执行文件位置**上溯三级推框架根：`<framework>/build/bin/st` | `tools/stpm/main.cpp:823-830`；`st.pkg` 缺失时报错文案在 `838-844` |
| F8 | 工具链里的 `build/` 还有三处消费方：`st clean`（整目录删）、JUnit 默认输出、`st init` 生成的 `.gitignore`/`build.sh` 模板 | `tools/stpm/main.cpp:957`、`343`、`931`、`923` |
| F9 | 自举脚本自己拼 `build/bin` 与 `build/obj/bootstrap`（不经 `st`） | `bootstrap.sh:131`、`150`、`224`（`bootstrap.ps1` 同构） |
| F10 | 仓库内脚本大量硬编码成品路径 `build/<档>/bin/<目标>` | `tools/*.py` 共 **23 个文件 / 29 处** |
| F11 | 测试里有一处把 `<工程>/build` 当固定夹具并整目录快照 | `tests/pkg_check_test.cpp:101`、`109-111` |

**实测互踩的四层**（`CONVENTIONS.md` §9.0④ 有表，这里是量化补充）：

- ①抢 `.tmp`：两进程共享同一 `.tmp` 名、各 120 轮 → **85 / 94 轮异常**，errno 2（ENOENT）；单进程 0 异常。
- ②混代产物：两"构建"各建 6 个同名单元 → 最终 6 个 `.o` 归属 **1 / 5** 分裂，**链接照常成功、零告警**。
- ③PCH 半截：把 `.gch` 截到 30% → GCC 报 `cannot read PCH file: 没有那个文件或目录`（**文件在，文案说不在**）。
- ④坏缓存：store 覆写 4 MB 对象 × 60 轮、restore 并发读 3000 次 → **889 次读到截断（≈30%）**，且坏条目跨构建存活。

复现（自建临时目录、不碰 `build/`、不联网；退出码 0 = 判据成立）：

```
python3 tools/build_isolation_repro.py tmp-race        # ①：双向判据（固定名>0 且 带pid=0）
python3 tools/build_isolation_repro.py mixed-gen       # ②：双向判据（混代>0 且 独立目录=0）
python3 tools/build_isolation_repro.py cache-corrupt   # ④：扫并发度给曲线 + 坏条目存活
```

③ 不在脚本内：它只需把已有 `.gch` 截断后调一次 GCC，属于一次性手工取证（无并发时序可量化）。

## 1. 候选做法

### A. 独立构建目录：`--build-dir <路径>` / `ST_BUILD_DIR`

**改动面**

| 面 | 内容 | 规模 |
|---|---|---|
| 公共接口 | `BuildOptions` 加 `std::string build_dir{}`（空=现状）——**加字段是加法**，不动既有语义 | `include/st/pkg/build.hpp:16-60` |
| 核心 | F2 的 5 处 + F3 的 1 处改成"`build_root(options) + "/<档>/…"`"；`st.pkg` 无需改（可选：允许顶层 `"build_dir"` 键） | ~6 处，一处新函数 |
| 命令行 | `st build/test/check/run/clean` 都解析同一开关；`ST_BUILD_DIR` 环境变量在 stpm 层读（不污染库层） | `tools/stpm/main.cpp` 4 个 command |
| 消费方 | F8 三处（clean 要删"它自己那个 build 根"、JUnit 默认输出、模板） | 3 处 |
| 自举 | F9：`bootstrap.sh/.ps1` 要跟着认同一个变量，否则自举产物落在 `build/bin` 而工具去别处找 | 2 个脚本 |
| 框架根推断 | **F7 会失效**：`/tmp/x/bin/st` 上溯三级不是框架根。要么保留"必须在 `<framework>/build/bin`"，要么补一条"找不到就用 `--framework`"的**显式**报错（现在已有该出口，但错误出现在 `st init`，位置远） | 1 处 + 文案 |
| 仓内脚本 | F10：23 个文件 29 处成品路径。**默认不变时全部不受影响**；一旦改默认，这 29 处要么读 `ST_BUILD_DIR`，要么继续瞎 | 29 处 |
| 测试夹具 | F11：`pkg_check_test` 的 `<工程>/build` 断言在**不传新选项**时仍然成立；若将来改默认，需同步 | 1 处 |

**代价与影响**

- **缓存不失效**：键是 `源路径 + 标志 + PCH token`（F6），**不含构建目录** ⇒ 换目录不产生"全量重编风暴"，
  但**工程单元会全编一次**（PCH token 变了一次）：dev 档实测 **337 个 `.o`**，单份 dev 树 **625 MB**（obj 266 + pch 117 + bin 242）。
  复现：`python3 tools/build_isolation_repro.py tree-size`（只读扫描，`--tree` 可指定别的构建树）
- **跨工作树已经不省**：同一份框架源在主树与工作树**各存一份缓存条目**（实测缓存 1865 MB / 1903 条，
  同一相对路径在主树 / 两个工作树里分别成条）——构建目录再多一份，cache 里**不会**再多一份（源路径没变）。
  复现：`python3 tools/build_isolation_repro.py cache-dup`（只读扫描，`--cache` 可指定缓存根）
- **风险**：`st clean` 的语义从"删 `build/`"变成"删配置的构建根"，若两者默认不同会有人误以为清干净了；
  `.gitignore` 模板只写 `build/`，自定义目录**不在忽略列表**里（把产物提交进仓库的隐患）。

### B. 构建锁：`.build.lock` + 持有者信息

**改动面**

| 面 | 内容 | 规模 |
|---|---|---|
| 公共接口 | `BuildOptions` 加 `std::string lock_path{}`（空=默认 `<build 根>/.build.lock`）与 `bool wait_lock{}`（false=立即失败） | `include/st/pkg/build.hpp` |
| 加锁点 | `build()` 与 `run_tests()` 的**入口**各一处（覆盖编译+链接+测试整段；测试运行期也占着锁，因为 `st_tests` 就在同一 `bin/`） | 2 处 |
| 平台层 | OS 级**咨询锁**：POSIX `flock`、Windows `LockFileEx`——必须放 `platform_*`（§10 第 1 条，lint L14 会拦） | 新建两个文件：src/pkg/platform_build_lock.cpp（平台实现）+ include/st/pkg/build_lock.hpp（端口与持有者结构） |
| 持有者信息 | 锁文件内写 `pid / 启动时刻 / 主机 / 可执行路径 / 命令行`，**仅用于报错文案**；锁本身随进程死亡由内核释放 ⇒ **不需要 stale 检测** | 同上一并 |
| 报错 | 拿不到锁时：`busy: 另一个构建正在跑（pid 1234, 09:33:12 起, /home/…/shuangtian）`，退出码用既有的 `125`（与"链接/构建失败"同口径） | `tools/stpm/main.cpp` |
| 测试 | 新建一个 pkg 层锁用例（同进程重入、跨进程持锁起一个醒着的子进程两条）；逆向验证：去掉 `flock` 调用后必须变红 | 1 文件 |
| 自举 | **不需要改**：自举不走 `st`（F9），它自己就是那个可能撞车的第二方——这条恰是 B 的**覆盖不到**的部分 | —— |

**代价与影响**

- **不解决并行吞吐**：它是"安全地失败/等待"，不是"让两个构建同时跑"。真正的并行仍要靠工作树（A 只是让同树也能并行）。
- **对缓存与产物缓存失效逻辑零影响**：锁不参与任何键，也不写 `build/` 里的产物。
- **`--wait` 语义要定**：默认建议 **立即失败并报持有者**（AI 循环里等待会静默拖长一轮），`--wait[=秒]` 显式选择等待。
- **嵌套调用**：`st run` 会先 build 再跑产物，若跑的那段时间也持锁，会挡住"边跑边编"——需要明确"锁覆盖到产物产出为止，运行期不持"。
- **锁文件本身的两个前提**（实测 `flock` 语义）：① 锁跟着 **inode** 走，所以持锁期间 `st clean` 把锁文件删掉会**静默失去互斥**（实测：删后新建同名文件即刻可锁，退出码 0）；⇒ 要么把锁放到 `build/` **之外**（如 `<工程根>/.st-build.lock`），要么让 `st clean` 先拿锁再删且不删锁文件。② 必须用**同一个解析路径**加锁：`exec 9>f; flock -n 9` 与 `flock -n f` 两种写法实测都正确互斥，但两套路径（符号链接 / 相对 vs 绝对）会各自成锁——这是核查项而不是已知缺陷。
  > 两条都能重跑：`python3 tools/build_isolation_repro.py lock-inode`（纯语义验证，不跑真构建）。
  > 实测结论：① 复现；② **不成立**——符号链接 / 硬链接 / 相对 vs 绝对都落在**同一把锁**上：
  > 互斥身份是 inode 而不是路径字符串，只有指向不同 inode 才各自成锁。脚本把这条差异如实报出。
- **Windows**：`LockFileEx` 是**区锁**且随句柄关闭释放——语义与 `flock` 对齐，同样不需要 stale 检测。

### C. 最小止血：`.tmp` 名带 PID + 缓存原子写（不解决归属）

| 改动 | 规模 | 治哪层 |
|---|---|---|
| 临时名加 pid（`<obj>.<pid>.tmp`） | 1 处（`build.cpp:1123-1124`） | ① |
| 缓存 store 改"写 `<key>/unit.o.<pid>.tmp` → rename" | 2 处（`378-379` 换成临时+rename） | ④ |
| PCH / 链接产物走临时+rename | 2 处（`573-574`、`1406-1407`） | ③ |

**代价小、收益明确，但②（混代产物）仍在**，而②恰恰是"链接成功、零告警、读数自相矛盾"的那一层。

### D. 现状（什么都不改，只靠纪律）

`CONVENTIONS.md` §9.0④ 的姿势 + 判据。**成本零，但每条判据都要人去执行**；
本息实测：同一时刻有两个 worker 在跑（一个在主树、一个在 `/home/x/redcase-wt`），
说明"靠自觉"在多 worker 编排下**已经不够**（正确姿势存在 ≠ 被执行）。

## 3. 推荐

**推荐：B（构建锁，默认开、立即失败并报持有者）先落地；A（`--build-dir`）作为第二期、opt-in、默认不变；C 作为 B 的伴生小改。**

理由：

1. **只有 B 覆盖 ④**。A 的致命盲点在这里：缓存键是"源路径 + 标志 + PCH token"（F6），
   **与构建目录无关**——两个 worker 用不同构建目录、同一份源，仍然算同一个键、仍会并发
   `copy_file` 到同一个 `~/.shuangtian/cache/objects/<key>/`。而 ④ 恰恰是症状最阴的一层
   （坏条目**跨构建存活**，"删了 `build/` 重编仍红"）。实测 30% 的读会拿到截断对象。
   > 复现：`python3 tools/build_isolation_repro.py cache-corrupt`（扫描并发度给曲线）；
   > 加 `--isolate` 是逆向验证：读侧共享锁 + 写侧独占锁 ⇒ 截断率归零。
   > 反过来看也解释了一个**已被实践验证**的事实：`git worktree` 隔离**顺带**把 ④ 也躲开了
   > ——因为键里含源路径，工作树与主树的键**天然不同**（实测缓存里同一相对路径确实各占一条）。
   > 所以 A（同树换目录）**继承了工作树的好处（①②③）却继承了共享缓存的互写（④）**——
   > 它是两种隔离度的中间态，而不是工作树的等价物。
2. **B 的代价是"机制"级的便宜**：2 个入口 + 1 个平台文件，且可以用 OS 咨询锁把
   "stale lock"这类最容易写出 bug 的逻辑整段省掉（进程死=内核释放，不需要 pid 存活探测）。
3. **A 的代价主要在别人的代码里**：29 处工具脚本 + 2 个自举脚本 + F7 的框架根推断耦合。
   而 A 的收益（同树并行）在**多 worker 场景下已被 `git worktree` 满足**（本息另一条线正是这么做的）。
   所以 A 的定位应是"给不方便开工作树的人（CI、容器、单分支流程）用的可选加速"，
   而非默认行为——**默认一变，F10/F11/F7 全部要同步**。
4. **C 便宜且与 B 不冲突**：`<obj>.<pid>.tmp` 与"缓存原子写"在锁之外再兜一层
   （锁失效时——例如有人手工绕过、或将来支持 `--no-lock`——不至于直接把坏对象写进缓存）。

**落地顺序（若批准）**

1. C 的小改（5 处，一天内可完成，含回归）；
2. B：`build_lock.hpp` + `platform_build_lock.cpp`（POSIX `flock` / Windows `LockFileEx`）→
   `build()`/`run_tests()` 入口持锁 → 报错文案带持有者 → `tests/pkg_build_lock_test.cpp`（含逆向验证）；
3. 观察一轮真实多 worker 编排（看是否出现"被锁挡下"的日志：它说明机制在工作，不是故障）；
4. 再评估 A：先把 F2/F3 收敛成一个 `build_root(options)` 函数（**这一步无论做不做 A 都该做**，
   因为 5 处各自拼串本身就是漂移源），然后加 `--build-dir`/`ST_BUILD_DIR`，默认不变；
   同步 F8/F9，并给 `st init` 模板的 `.gitignore` 加上自定义目录。

**明确不做**：不把 `build/` 改成"每进程自动唯一"（会毁掉增量构建与 `st run` 的可预测路径）；
不在 `st` 里自动探测"另一端有构建"再自动改道（隐式改变产物位置，排查成本远高于收益）。

## 4. 验收口径（给将来落地用）

- B：两个进程同时 `st build` 同一棵树 → 第二个**立即**以 `busy:` + 持有者信息退出（退出码 125），
  且第一个的产物**逐字节**等于单独跑的产物；杀掉持锁进程后锁自动释放（无需 `--force-unlock`）。
- C：两进程并发编译同一棵树 → 无 `rename` 失败；`~/.shuangtian/cache` 里不出现读不出头的 `unit.o`。
- A：`ST_BUILD_DIR=/tmp/x st build` 后 `build/` 目录**未被创建**，产物与默认位置**逐字节相同**；
  `st clean` 清的是 `/tmp/x` 而不是 `build/`；`st init` 在自定义目录下给出**明确**的 `--framework` 提示而不是错误地推出框架根。
