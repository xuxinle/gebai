# 霜天 vs 浏览器 字体渲染对照 —— 全字符集 + 全字号阶梯（2026-10-06）

> 口径：**真窗口** Chromium（Xvfb，headed，非 headless）vs 霜天渲染器，两侧**同一套字体**
> （逐行用 CDP 导出浏览器实际字体归属核对：`DejaVu Sans` / `Noto Sans CJK SC` / `DejaVu Sans Mono`）、
> 同画布 DPI（deviceScaleFactor 1.5）、同前景/背景色、同一份行表（由 `tools/gen_text_ab.py` 单源生成）。

## 一、结论（修正后的真实差距）

| 量 | 霜天/浏览器 |
|---|---|
| **总墨量** | **0.93（字符集页）/ 0.96（字号阶梯页）** |
| **实心像素（覆盖率 >0.85）** | **0.87~0.90（一致偏少）** |
| 过渡像素（0.15~0.85） | ~1.00（基本持平） |
| 字形盒 高/宽 | 1.000（**没有画扁/画宽**） |
| 逐行平均显著差异 | 14.9%（字符集）/ 11.5%（字号） |
| 小字号（10~12px） | 0.90~0.94，**更明显** |

**即：霜天的字形几何是对的，差的是"墨的深浅"——笔画没到满黑，而不是画细了。**

## 二、根因（逐字形对账，非推测）

同字体、同字号（逻辑 15px × DPI 1.5 = 22.5 物理像素）、逐字形（`tools/freetype_ink_decompose.cpp`）：

| 量 | 结果 |
|---|---|
| 轮廓几何（面积/周长/包围盒，霜天 vs FreeType） | **比值 1.0000**（`tools/glyph_outline_compare.cpp`）——CFF 解释器**精确** |
| 霜天 / FreeType「hinting 与加墨都关」 | **0.98~1.00**——栅格化与覆盖率算法**精确** |
| FreeType 的 **CFF hint 执行**贡献 | **×1.06~1.08** |
| FreeType 的 **stem darkening**（CFF 默认开）贡献 | **×1.06~1.09** |
| 两者叠加 | **×1.12~1.19** |
| 霜天 / FreeType 默认档 | **0.885~0.907**（汉字） |

**拉丁**（DejaVu，TrueType，无 CFF hint 可执行）**不受影响**：霜天 1.09 / FreeType 关加墨 1.00
——与"宏观对照里拉丁比汉字好"完全一致。

⇒ 差距**全部**来自 FreeType 默认开启的两个机制，霜天一个都没有：

1. **CFF hint 执行**：`hstem`/`vstem`/`hintmask`——把笔画边缘吸附到像素网格、
   保证笔画宽度不为零。霜天的 Type2 解释器**读了 charstring 但不执行 hint 操作符**
   （注意：这与 `grid_fit` 不是一回事——`grid_fit` 是**几何网格拟合**，
   而且实测它在这里是负收益：开启后实心比从 0.873 掉到 0.733）。
2. **stem darkening**：CFF 引擎默认的加墨，随 ppem 衰减（小字号更强——与实测"小字号偏差更大"一致）。

## 三、已排除的路线（别再试）

| 候选 | 实测结论 |
|---|---|
| 覆盖率 gamma 压黑 | γ0.8 才能补回总墨量，但**实心比冲到 1.18**（过黑）、过渡掉到 0.81 |
| 亚像素低通滤波改强度/关闭 | 对**墨量无影响**（0.936 不变），只改锐度（实测它是**锐度**旋钮，不是墨量旋钮） |
| `grid_fit` 关/轻/正常 | 关掉最接近（实心 0.873 / 过渡 1.001）；打开反而**实心掉到 0.733**、过渡 1.27 |
| 扁平化容差、超采样密度 | 前一轮已排除（端指标 <0.1%） |
| 几何（字形被画扁/画窄） | 排除：轮廓 1.0000、盒高/盒宽比 1.000 |

## 四、候选修法（待你选）

| 方案 | 做法 | 代价 / 风险 |
|---|---|---|
| **A. 按字形覆盖率直方图补偿**（推荐先做） | 逐字形读覆盖率分布，把不足的像素**有界**抬到满（只抬不压，增量上限可设） | 低：几何不动、性质是"在覆盖率层面补回 FreeType 那两步造成的差"；但它是**近似**，不是机制复刻 |
| B. 执行 CFF hint | 在 Type2 解释器里实现 `hstem/vstem/hintmask` + 宽度量化 | 高：CFF charstring *不存* 标准宽度（必须从 stem hints 推），工作量大；但这是**唯一"正确"的路**，且顺带解决小字号笔画消失 |
| C. 实现 stem darkening 曲线 | 按 ppem 的加墨曲线 | 中：曲线参数需标定，且它**只解释一半**差距 |

> ⚠ **默认值是产品决策（按约定不擅自改）**：A 的"增量上限"、以及要不要动
> `fit` 的默认档，都需要你定；我只提供候选+实测差异。

## 五、量尺自身修正记录（这轮最贵的一条）

以下四处口径错误都**实际发生过**，每一处都会把方向判反：

1. **字体不同源**：对照页原先写 `'Segoe UI','Microsoft YaHei'`——Linux 上两名皆缺，
   浏览器落到 `Liberation Serif` + `Noto Sans CJK **JP**`，霜天走自己的链（`DejaVu` + CJK **SC**）。
   修：两侧显式同族名 + CDP 导出实际字体做断言。
2. **`FT_Bitmap::width` 在 LCD 位图里是子像素数**（`pitch` 才是字节数）——按像素读会越界读
   2/3 字节，墨量虚高 **3 倍**（"中"402.7 vs 真值 134.6）。
3. **`FT_LOAD_NO_SCALE` 下坐标已是字体单位**（不是 26.6 定点）——再除 64 会小 64 倍
   （"一"的周长 1997 被读成 31.2）。
4. **两侧基线口径不同源**：浏览器 `top:` 是行盒顶边（基线在 `ascent`，Noto CJK ≈0.88 em）；
   霜天 `draw(origin)` 的 origin 是文本框顶（基线在字体 **ascender** ≈1.16 em），
   @15px/1.5 实测**低 7.8 物理像素**。按同一 y 带裁切会同时截掉霜天字形下部、
   切进下一行上部——把汉字墨量比读成 0.41~0.65，并据此得出**方向相反**的结论
   （"霜天 CFF 少墨"）。修：**两侧各自按行投影切带、按序配对**。

# 追加：方案 B2 + C 落地（2026-10-06 晚）

## 做了什么

**B（CFF hint 执行）**：Type2 解释器原先**跳过** `vstem/hstem/vstemhm/hstemhm`（只数个数、
丢掉位置与宽度）。现在会记录成 `StemHint{lo,hi,vertical}`（含 hintmask/cntrmask 的隐式提示），
按字形缓存，并在拟合里**优先采用**（几何反推只补缺）。亚像素分支横轴是 3 倍，
提示按**同一空间**换算后重跑一次拟合（`options.grid` 承担倍率，调用方只传物理像素）。

**B2（hints 的用法做全）**：`Light` 档只拟合竖笔画（横笔画靠几何反推容易把撇捺的横跨
误判成一横）。但 `hints` 是字体给的数据，**没有猜错的风险**——于是横轴的 hints 在任何档都采用。
CJK 的横提示远多于竖提示（实测「霜」19 条提示全是横），这一开口才有意义。

**C（stem darkening）**：按 FreeType 的 `darkening-parameters` 四点折线
（宽度≤0.5px → 加 0.4px；1px → 0.275px；1.667px → 0.275px；≥2.333px → 0）
把**每条笔画**的两侧各向外挪半个加墨量。要点三条：

1. **只对 CFF 字体做**——这是 FreeType 自身的规则（`cff` 引擎默认开、
   TrueType 靠指令保证笔画不为零宽）。实测证据：DejaVu（真型）本来就比浏览器**深 1.09**，
   不分档就会"补了 CFF、过深了 TTF"。
2. **按每条笔画的宽度查表**（细笔画加得多，宽笔画自动归零）——所以它天然**只在
   小字号生效、大字号自动关闭**，不需要额外的字号分档。
3. **几何外扩**而非覆盖率映射，因此与 gamma 正交、可叠加。

## 实测效果（28 行字符集页，与真窗口浏览器逐带比对）

按**字类分组**（这轮最重要的口径改进：此前只看总平均，被三类的相反趋势互相抵消）：

| 档位 | 汉字 墨量/实心/过渡 | 等宽 墨量/实心/过渡 | 拉丁 墨量/实心/过渡 |
|---|---|---|---|
| 基线 `fit=light`（无加墨） | 0.928 / 0.970 / 0.874 | 0.959 / 1.127 / 0.810 | 0.942 / 1.092 / 0.786 |
| **+加墨（CFF only）** | 0.940 / 0.977 / **0.960** | 0.959 / 1.127 / 0.810 | 0.942 / 1.092 / 0.786 |
| +加墨 γ0.95 | 0.977 / 1.115 / 0.905 | 0.992 / 1.200 / 0.776 | 0.971 / 1.151 / 0.763 |

**加墨把汉字的过渡像素比从 0.874 提到 0.960**（更接近浏览器，即笔画更"满"），
而拉丁与等宽**逐位不变**（自动只作用于 CFF）——这正是想要的形状。

## 仍未闭合的缺口（如实记录）

| 项 | 数值 | 说明 |
|---|---|---|
| 汉字实心比 | 0.977（加墨后） | 已很接近 1.0；**再压 gamma 会过冲**（γ0.95 → 1.115） |
| 拉丁实心比 | 1.092（加墨不作用于它） | 真型字体在 DPI 1.5 下已比浏览器深 ~9%；**gamma 是全局的、动它会砸坏汉字** |
| 等宽实心比 | 1.127 | 同上（DejaVu Sans Mono 也是真型） |
| 总墨量 | 0.93~0.97 | 缺口主要来自 latin/mono 的过渡像素（0.78~0.81） |

⇒ 结论：**汉字这条线已基本对齐**；剩下的缺口是"真型字体（DejaVu 系）在 1.5 DPI 下
比浏览器略重"，而修法必须**按字体分档**（全局 gamma 做不到）。
这一条写入 BACKLOG 待定（改默认值属产品决策）。

## 量尺/实现过程中踩到的坑（都写进代码注释）

1. `FT_Bitmap::width` 在 LCD 位图里是**子像素数**（按像素读会越界读 2/3 字节，墨量虚高 3 倍）。
2. `FT_LOAD_NO_SCALE` 下坐标**已是字体单位**（再除 64 会小 64 倍）。
3. 两侧**基线口径不同源**（浏览器行盒 vs 霜天文本框顶，@15px/1.5 差 7.8 物理像素）——
   按同一 y 带切会把汉字墨量比读成 0.41~0.65，方向相反。
4. hint 换算的**空间口径**：`stems_from_hints` 内部会乘 `grid`，调用方只传物理像素；
   亚像素分支横轴是 3 倍。两处错任一都会让 `hint_stems` 恒为 0（看起来像"字体没有 hints"）。
5. **逆向验证时读到了缓存**：位图缓存按尺寸等字段索引，改了实现但不换尺寸时，
   同一个可执行文件内会直接命中上一轮的位图——那会让回归测试**恒绿**。


## 最终数字（应用默认档：拟合 light + 墨量补偿 + 笔画加墨）

| 字类 | 改前 墨量/实心/过渡 | 改后 墨量/实心/过渡 |
|---|---|---|
| **汉字**（Noto Sans CJK SC，CFF） | 0.930 / 0.993 / 0.859 | **0.943 / 0.998 / 0.965** |
| 等宽（DejaVu Sans Mono，真型） | 0.963 / 1.158 / 0.783 | 0.963 / 1.158 / 0.783（不变） |
| 拉丁（DejaVu Sans，真型） | 0.943 / 1.097 / 0.777 | 0.943 / 1.097 / 0.777（不变） |

**汉字这条线已基本对齐**（实心像素比 0.998、过渡像素比 0.965）。
剩下的缺口在**真型字体偏重**（拉丁 1.097、等宽 1.158）——加墨按设计不作用于它，
而全局 gamma 修不了（压 gamma 会把汉字冲到过黑）。见 BACKLOG P1。

## 两项能力的落地状态（如实）

| 能力 | 状态 |
|---|---|
| CFF hint 解析（`StemHint` / `FontFace::stem_hints`） | **默认生效**（解析与缓存总是做） |
| CFF hint **采用**（喂进拟合） | **默认关闭**（`ST_TEXT_USE_FONT_HINTS=1` 开启）：收益小（实心比 1.033→1.013）且破坏位图 padding 不变式 |
| **笔画加墨**（`set_stem_darkening`） | **应用默认开启**（`ST_TEXT_DARKEN=0` 关）：汉字实心比 → 0.998，拉丁/等宽逐位不变 |


## ⚠ 口径更正（2026-10-06 续）：分族测量推翻了"拉丁/等宽偏重"那条

早先本节按"字类分组"报出汉字 0.99 / 等宽 1.16 / 拉丁 1.10（实心比），据此开了
"真型字体偏重、需按字体分档"的方向。**那是量尺错**：分类按行的**标签文本**做，
而标签里常混两种字（「常规 霜天组件画廊 Regular」「text #0F172A 正文」…），
于是一批**以拉丁/等宽为主**的行被算进了汉字类。

新增分族页（`tools/text_ab_families_page.html`：同一字族单独成行、只变字号）后：

| 档位 | 汉字 实心 | 拉丁 实心 | 等宽 实心 |
|---|---|---|---|
| **应用默认** | 0.946 | 0.953 | 0.964 |
| 关拟合 | 0.903 | 0.882 | 0.944 |
| 关拟合 + γ1.0 | 0.991 | 0.932 | 1.010 |

⇒ **三类字都在 0.95 附近，没有系统差异。** 剩下的唯一一致缺口是**过渡像素比偏高约 5%**。
分类已改为**数据**（生成器按实际渲染文本写入 JSON 的 `class` 字段），不再靠猜字符串。


## ⚠ 参照敏感性（本轮第二条量尺教训）

"过渡像素偏高 5%"是用浏览器**原生 1.5×**当参照量的。为排除 1.5× 光栅化的谐波走样，
让浏览器在 `deviceScaleFactor=3` 渲染后降采样到 1.5×、用同一套量尺重测：

| 参照 | 拉丁 实心/过渡 | 汉字 | 等宽 |
|---|---|---|---|
| 原生 1.5×（用户实际链路） | 0.953 / 0.937 | 0.946 / 0.998 | 0.964 / 0.970 |
| 3× → 降采样 1.5× | **1.038 / 0.904** | **1.029 / 0.988** | **1.101 / 0.943** |

**同一个霜天二进制，只换参照定义，实心比 0.95 → 1.03~1.10。**
⇒ 该量级的差异落在"参照怎么定义"的噪声里，**不构成可追的缺陷**。
按"参照取用户实际那条链路"的约定，**以原生 1.5× 为准**；
在换参照之前不要再改滤波/gamma 去追那几个百分点。
