# 验收判据总表（收单前逐项勾 · 收完还要三拍）

> **收单前：按「交付类型」找到那一行，逐项勾完才算收。**
> **收完之后：还有三拍（§3）——账没销完，这一单在下一息的眼里就还在做。**
> **勾不动的（测量窗口不干净、拿不到 git、脚本没入仓…）就先别收**——那是「本项未核」，不是通过。
> 每道门只给一句话 + 命令 + **指过去**；**判据原文以各自详述处为准，本文件不存第二份真相**。

**这份文件是什么**：一张**按交付类型检索的清单**。本仓的门已经有十几道，但**散在十几处**——
每一道都在它自己的位置上写得很好，却没有一处能让人**一次看全**。于是收单时漏查不是例外，是常态：
本窗口 18 单里，「收单时漏掉某一门」反复出现（真实代价见文末 §4）。

**它不回答「这道门为什么存在」**，只回答「收这一单，我要逐项确认哪几件事」。
想知道某道门为什么长这样、踩过什么坑，顺「详述」列点进去——那里才是判据的家。

**用法**：`☐` 表示这一项还没核。勾之前把**命令输出**留在收单记录里（不是"我记得跑过"）。

## 1. 按交付类型分行的勾选表

四种交付类型，各自**必须**过的门不同。一单可能跨两类（如「机制 + 新增脚本」）⇒ **两行都要勾完**。

### 1.1 机制类（拦截 / 闸门 / 清理 / 权限 / 范围限制）

| 交付类型 | 必须通过的门（逐项勾） | 判据命令 | 详述 |
|---|---|---|---|
| **机制类** | ☐ **正向通过**：本该拦的拦住了 / 本该清的清干净了 / 本该放行的放行了<br>☐ **反向通过**（三种写法按本单实际面至少落一种，写不出就不算有）：**不得 X** / **别的合法路径行为不变** / **作用域外的对象一个没被碰**<br>☐ **会红的反证**：把实现退回旧版，指定用例必须红（不红 = 这条断言其实拦不住东西）<br>☐ **锚点**：一条 `present: false` 都不许有<br>☐ **锚点未过期**：`stale_hints` 看过一眼（退役词 / 只在注释行命中 = 提示不是退化，但要看）<br>☐ **引用可解析**（仅当本单同时是文档交付；否则跳过，但**别把跳过的算成通过**） | ☐ `bun test <文件> [-t <用例名>]`（正向 + 反向）<br>☐ 逆向验证脚本一次（如 `python3 tools/theme_reverse_verify.py`；生生的机制用 `python3 packages/agents/src/agents/shengsheng/reverse_verify.py`）<br>☐ `python3 tools/shengsheng_sentinel.py --anchors`<br>☐ `python3 tools/check_docs.py`（仅文档形态） | `packages/agents/src/agents/shengsheng/shengsheng.md` §六「机制类交付必须有反向断言」+ §七「收」（口径四条）<br>`docs/PITFALLS.md` 场景 17（验收一单机制类交付）<br>`docs/PITFALLS.md` 索引 A（绿而无效的五种形态）<br>`docs/PITFALLS.md` 场景 15（写逆向验证脚本） |

**为什么这一行的门最多**：机制类交付里，真正容易坏的是**边界**那一侧，而不是功能那一侧。
所以正向全绿、反向缺失时，单子看上去完全成功。缺正向会红（“没做”被人看到）；
缺反证要等回退才暴露；而“碰了不该碰的”在正常路径上**根本不发信号**。

**三条容易漏的子项**（都不是可选项）：

- **反向要能真的抓住它声称防的事**：退回实现后那条反向用例**必须红**。不红 = 它写的是注释。
- **消灭一个缺陷时同步改掉描述它的锚点**：旧锚点的特征串可能**正是**新修复要消灭的形状 ⇒
  留着它等于逼后来人把 bug 写回去。所以「锚点全绿」还不够，要看 `stale_hints`。
- **锚点只在注释里时它不守行为**：`present: true` 也可能只是注释里还有那句特征串。
  这正是索引 A 的第⑤种形态——“我查的是行为、是代码、还是一个字符串？”
  所以 `stale_hints` 那一眼不是礼节，它单独靠代码行统计才能把这类假绿挑出来。

> `git ls-files --error-unmatch <路径>` 补一下（§2 第三道门）。

`git ls-files --cached` 里有这个键。`check_docs.py` 已替你做这件事，**但只在有 git 的仓库里**——
在没有 `.git` 的目录里跑，它以 `exit 2` 告诉你「本项未核」，**不要把它读成绿**。

**「测量窗口」与「提交范围」是同一种病的两面**：都是**你以为的院子与真实的院子不是同一个**。

——所以任何自测都发现不了它们，只能靠收单这一眼。

## 3. 收单之后（三拍）

§1 与 §2 查的都是**成果本身**；这一节查的是**账**。成果查得再干净，账上留着一笔没销，
下一息读到的就是另一个故事。本窗口反复犯的错**全在这一半**，而且它们的共同形状是同一个：
**收单那一刻看到成功回显，注意力被占满，忘了后面还有拍**。

### 第〇拍（先于三拍）：核「东西在不在仓」

> ☐ `git status --porcelain <本单涉及的每个文件>` **必须为空**。
> 不为空 ⇒ **先派提交单，不 `collect`**——`collect` 确认的是「我读过它的报告」，不是「成果进了仓」。

本窗口实测：一单收得干净、回显全绿，而它的交付改动仍停在 `??` / `M` 上（取证见 §4 第一条；
门本身是 §2 第三道门）。点名文件的好处是**它只核你点名的那些**：别人在同一棵树上的改动
不会让它变红，也不会被它冒充成「本单已提交」。

### 三拍

| 拍 | 动作 | 为什么必须 | 判据命令（☐ 逐项勾） | 详述 |
|---|---|---|---|---|
| **第一拍** | ☐ `shengsheng_collect action=collect`（带 `next=` 报告里的「建议下一条」） | 报告入台账、worker 标 idle、在途清除、租约释放——**这是「这一单结束了」唯一的落盘动作** | ☐ 回显含 `收藏完成：<别名>｜<领域>` 与 `- 台账：…（已追加）`<br>☐ 台账确实多了这一节：`grep -c '｜<别名>｜' .evolve/ledger.md` = **1**（幂等键 `<!-- collect:<会话>:r<轮次> -->` 也在）<br>☐ 若回显是「台账已有该 worker 的记录（幂等跳过）」⇒ **本节没追加**，别再当它新收了 | `packages/agents/src/agents/shengsheng/shengsheng.md` §七「收」<br>`shengsheng.ts` 的 `collect` 分支（幂等键取 `max(在途,池)` 的轮次） |
| **第二拍** | ☐ `shengsheng_state action=seed_done match=<该方向原文>` | **不销种子，种子队列就会骗下一息的你**：它读到的仍是「这项还没做」，于是**再派一次**（真重复烧一条 worker 命） | ☐ 回显 `种子销账（已完成）：[…]——队列剩 N 条`，且 N 比拍前小 1<br>☐ 定向复核（`<独特串>` 取方向原文里的**长**片段，别取关键词）：`awk '/^## 种子队列/{f=1;next}/^## /{f=0}f' .evolve/control.md \| grep -c '<独特串>'` = **0** | `packages/agents/src/agents/shengsheng/shengsheng.md` §五「择」（择定先 `seed_add`、派出去即销账、销账按方向**精确**匹配） |
| **第三拍** | ☐ 判 `shengsheng_collect action=retire mode=idle` 还是**留池复用** | **不退役，池子就会骗下一次派工**：活动额度数的是**池里所有条目**（running + idle 一起），而 `collect` 只把状态改 idle、仍留在池里——于是你以为「池里还有位置」，派新领域的单时 `dispatch` 却回「活动 worker 已达上限」（本窗口台账记过一次被顺延） | ☐ 退：回显 `已退役（仅清出池）：<别名>`；`awk '/^## worker 池/{f=1;next}/^## /{f=0}f' .evolve/control.md \| grep -c '<别名>'` = **0**<br>☐ 留：`shengsheng_state action=read` 汇总行的 `池 N（M idle…）` 里 M ≥ 1，且池行中该别名那行的状态位写的是**空闲**（不是「运行中」），并**在断点里写了为什么留**<br>☐ 两种都可以，但**必须当场选定一种并落盘**（不判＝留在池里，等于默认选了「留」） | `packages/agents/src/agents/shengsheng/shengsheng.md` §七「收」（留池与退役三情形、清池三种力道）<br>`shengsheng.md` §八「天行」（额度只挡新建）+ §五（活动 worker 上限）<br>`shengsheng.ts` 的 `activeWorkerLimit` 与 `state` 的 `active = state.workers.length` |

> **三拍没走完，这一单就不算收完——因为下一息的我会以为它还在做。**

### 三条容易踩歪的（把判据写成「看数变了」就会被骗）

- **种子数变少 ≠ 销对了**：第一拍带 `next=` 时会**同时入一条新种子**（`collect` 把「建议下一条」
  以 `回收报告 <别名>` 为来源 push 进队列）——于是 `seed_done` 销掉的那一条，可能正好被
  **同一单**的「建议下一条」补上。可看实体证据：这一节本身的方向就是这么入队的
  （种子队列里它的来源列写着 `回收报告 verify-playbook`）。⇒ 第二拍的判据是**定向命中数归零**，
  不是总数变小。
- **关键词 grep 会假阳性**（本窗口实测）：拿本单元领域短名去种子队列里 grep，命中 **1** 条；
  而那一条不是「上一单没销干净的旧账」，是**从上一单的建议下一条里生出来的另一条种子**
  （来源列写着 `回收报告 <上一单别名>`）。可对照：同一次用**已销方向原文的长片段**去 grep，得 **0**。
  ⇒ 取方向原文里的**长**片段，或直接信 `seed_done` 回显那个数。
- **`retire mode=idle` 只清出池，不删会话**：盘上的会话还在（回显会明说「需彻底清理由 `mode=delete`」）。
  所以第三拍的「池数变少」**不等于**「会话没了」——两者别混说。

### 退役的判断依据（不是「总是退」）

- **退**：领域已收敛（同域没有下一个方向）or ctx 过**复用建议线**。
- **留**：同域还有下一单要派——复用它的上下文最省钱。
- **必须退**（这不是选择）：ctx 过了**真实模型窗口**。两个量不可互换、不可互相冒充，
  口径与 env 见 `packages/agents/src/agents/shengsheng/shengsheng.md` §十一。

### 与 §2 同一种病

§2 的两道门守「你以为的院子和真实的院子不是同一个」；三拍守的是
「**你以为的账和下一息读到的账不是同一本**」。它们都不在成果里，所以任何自测都发现不了
——只有收完单再回头看账这一眼。

## 4. 本窗口踩过的漏查（真实案例，让表不死）

这一节是这份表**存在的理由**。下面三条在本窗口（2026-10-17，18 单）真发生过，不是假设。
完整取证在各自的详述处；这里只留「漏了哪道门 / 当时看得见什么 / 实际发生了什么」。

- **漏核「是否已提交」⇒ 收了单，成果全在工作树。**
  第 55 息收 `pgrep-1`：交付的六份文件全都改好了，重跑的测试与类型检查也全绿，
  **但没有一样进了仓**。收单的人看的是「工作树里的成果」，而下一个从干净克隆起来的人看到的是零。
  漏的正是 §2 第三道门（`git ls-files --error-unmatch`）。
  该单自己的自述就写着「未提交，工作树改动」——**那句话当时就在眼前，没人把它当阻塞项**。
  旁证归处：`docs/PITFALLS.md` 场景 16（提交与交付）；五处材料的原始语句里无此事后复盘。

- **漏核「引用是否已入仓」⇒ 引用悬空三次。**
  ① pty 四工具（第 27 息）：`docs/BACKLOG.md` 与用例注释引用了还没 add 的脚本；
  ② `wait_probe.sh`（第 58 息）：那批“等待纪律”的实测数据被引了，脚本却还在 `/tmp`；
  ③ lease 三脚本（第 61 息）：`DESIGN.md` 引的脚本从来没有入过仓。
  三次都是同一形态：**本地一切正常**（磁盘有、仓里没有），所以校验器绿、作者也绿，
  直到有人清理工作树、切分支或在干净克隆里读文档才断。名单与提交号在
  `tools/check_docs.py` 头部（它是判据从「磁盘实存」升级为「实存 ∧ 已入仓」的直接原因）。
  漏的是 §1.2 那两道分开的门。

- **漏核「测量窗口」⇒ 同一份代码、同一台机，两轮数字不一致。**
  `bun test` 第一轮 **86 pass / 2 fail**，第二、三轮 **88 pass / 0 fail**。
  不是噪声也不是 flaky——当时**另一个人在跑逆向验证**，源码正处在回退态，所以读到的是缺陷版。
  这个坑有两个方向：既会假红（读到别人的回退态），也会**假绿**（基线本身是回退版时，
  你以为自己改对了）。漏的是 §2 第一道门。

**这三条的共性**（也是这张表为什么按「类型」而不是按「工具」分行）：
漏掉的都不是**被测的东西**，而是**测量的前提**。前提坏了，量出来的每个数都成立——
只是量的不是你以为的那个对象。所以这些门**必须能在收单时逐项勾**，不能指望「跑测试时会发现」。

## 5. 这道表自己怎么维护

- **只加"收单时会漏"的门**。收单时想不起来的门才配进表；能被工具自动判、且判了必然会拦住你的
  项（如 `st test` 有红就编不过），记一笔命令即可，不必展开。
- **不复制判据原文**。每道门的"为什么"只活在它的详述处；本表若把那句话抄过来，
  两处就会漂移，而漂移的那一处永远是本表（它没人跑）。新增一行时先问：
  **这句话在详述处已经有了吗？** 有 ⇒ 指过去。
- **新交付类型**：先看它是否落进已有四类。落不进去（如"依赖升级""跨仓协议变更"），
  再开一行——但要有**一次真实漏查**作为它的出生证明，否则它只是又一个没人勾的框。
- **先问它属哪一半：查「成果」还是查「账」**。§1/§2 的每一项都能在**成果里**当场看见（测试红绿、路径是否入仓）；
  §3 的每一拍只能在**账里**看见（种子队列、池、台账）。放错一半的判据会变成偏方：
  拿「回显说成功」当「成果在仓」，或拿「文件改了」当「账已销」。
- **每条案例都要能被下一单重演**（命令 + 判据 + 当时数字）。案例写成"我们曾经注意过质量"
  就死在这里了。
