# `st check`：跨编译器检查（只查不产出）

## 1. 它解决什么

同一份源码在 **GCC 下全绿**、在 **Clang 下编不过** 的情况真实存在——两族对同一处
未定义/未指定行为的判断不同。本仓库实测拓出过 9 处**自家代码**的真缺陷
（未使用的私有字段、未使用的 lambda 捕获、`size_type → difference_type` 隐式变号、
死函数、死常量……），每一处都**只有 clang 报**：

> 这一类问题在 GCC 上永远不会现形，所以"只用 GCC 编一遍"永远发现不了它们。

原先唯一的发现手段是 `st build --toolchain=clang`——一次**全量构建**（37 s），
要产物、要链接，只为了看诊断。`st check` 把那一步换掉。

## 2. 成本（实测，本机 28 逻辑核）

| 口径 | 耗时 | 产物 |
|---|---|---|
| `st check --toolchain=clang` | **15.0 s** | 无 |
| `st check`（默认 gcc） | 21.3 s | 无 |
| `st check`（增量，无变化） | **~0.5 s** | `.check_state` 更新（若查了） |
| `st build --toolchain=clang`（全量） | 37.3 s | 二进制 + `.o` |
| `st build`（gcc 全量） | 36.3 s | 二进制 + `.o` |

- **2026-10-28 更新：check 现在也建/读 PCH**（同编译器时），并支持**增量判定**——记录
  上次查过时每个单元的源+依赖内容哈希到 `build/<profile>/.check_state`，下次只查
  变化（或首次）的单元；`--force` 强制全量（CI 用）。实测：155 单元首次全量
  with PCH 从 59s → 38s，无变化时增量 <1s，改一个文件只查相关单元。
- 旧版不读 PCH 的顾虑（跨编译器 .gch 不兼容）已不成立：`build/<profile>-<tag>/pch/`
  按编译器隔离目录（`profile_directory` 含工具链 tag），clang 吃到的是自己编的 .gch。
- **副作用**：写 `.d`（依赖清单，`-MMD`，增量判定输入）与 `.check_state`（增量状态）；
  不写 `.o`/标志指纹、不碰共享对象缓存、不链接。

## 3. 与 `build` 的关系：**共用一段，不可能分叉**

`check` 不是另写一条路径，而是给 `build` 加了一个出口：

```
BuildOptions::check_only = true
  → 单元枚举 / 框架引用 / 嵌入生成物 / 第三方放宽 / 按族收敛标志 / 目标三元组 / 并发推导
    （以上全部与 build 完全相同）
  → 最后一步：-c -o x.o 换成 -fsyntax-only；不写产物；不链接
```

为什么刻意如此：上面那几件（尤其是**嵌入生成物**与**框架单元标记**）很容易只改到一半。
两套枚举一旦分叉，症状是"检查过了但编不过"——那时人会先去怀疑编译器差异，而不是枚举不一致。
共用一段除了省代码，更重要的是让两者不可能分叉。

### 增量判定（2026-10-28）

旧行为每次全量查全部单元（"恒绿哨兵"：源码没变也必须全查一遍，155 单元实测 ~59 s）。
改为**内容哈希增量**：check 成功后把每个单元的源+依赖（`.d`，`-MMD` 产出）哈希写入
`build/<profile>/.check_state`；下次只查与记录不一致（或首次）的单元，`--force` 强制全量。
语义从"每次都全量查"变为"只查有变化的"——与构建增量同一哲学；CI 用 `--force` 保持全量兜底。

## 4. 查得出 / 查不出

| | 内容 |
|---|---|
| **查得出** | 编译期诊断：类型错误、未使用符号、隐式转换/变号、未使用捕获/字段、死代码、格式串、`-Werror` 全开的严格集 |
| **查不出** | 链接期问题：**ODR 违反、符号缺失、ABI 不匹配**。`-fsyntax-only` 不生成代码、不解析符号——这几类只有真链接才暴露 |

本仓库恰好有后一类的前科（缺陷 28 重复符号、缺陷 30 改了头文件不重编 →
运行期 access violation）。所以：

- **`st check`**：高频、便宜、无副作用 → 适合每次改动后跑；
- **`st build --toolchain=clang`**：低频、完整 → 提交前或 CI 跑一次。

两者是分工，不是替代。

## 5. 用法

```bash
st check                          # 用默认编译器查（本机 gcc；增量：只查有变化的）
st check --force                  # 全量查（忽略增量状态；CI 用）
st check --toolchain=clang        # 跨编译器门禁（主要用法；PCH 按编译器隔离目录）
st check --profile=debug          # 换档位（标志集随之变化）
st check -j 8                     # 限并发（默认 = 硬件核数）
```

退出码：全部单元通过 → `0`；任一单元报错 → `1`，并把编译器原文打出来
（含**源文件名与行号**，直接可定位）。

## 6. 回归护栏

`tests/pkg_check_test.cpp` 三条，全部用**自建的最小工程**（2 个源文件）在临时目录里跑，
几百毫秒完成——不用本仓库当被测对象（那要 20 s 以上，会撞用例软超时上限）：

| 用例 | 判据 |
|---|---|
| `check_only_writes_no_artifacts` | 检查前后 `build/` 与源码目录**逐项完全一致**（路径 + 大小 + 修改时间）。只数文件个数不够：原地覆盖同一个 `.o` 也能骗过计数 |
| `check_only_finds_broken_source` | 故意写一处类型错 → 必须**失败**，且报错里出现源文件名。否则上一条的"无副作用"会被"恒不报错"冒充 |
| `check_only_checks_every_unit_not_incremental` | 连续查两次，两次的单元数相同且都 `> 0`。若沿用增量判定，第二次会是 0——**恒绿的检查比没有检查更糟** |

**逆向验证结果**（逐条回退实现 → 对应测试必须变红）：

| 回退项 | 结果 |
|---|---|
| 不跳过"写产物"（照常改名写 `.o`） | `check_only_writes_no_artifacts` 变红 ✅ |
| 不跳过"增量判定" | `check_only_checks_every_unit_not_incremental` 变红 ✅ |

## 7. 它拓出的第一处缺陷

接入当天就抓到一处：`src/pkg/build.cpp` 的 `std::atomic<bool> dep_warning` 是移除 MSVC
支持时留下的**死变量**（原先只在 MSVC 的依赖清单降级告警里用到）。GCC 不报，clang 报
`-Wunused-variable` → `-Werror` 下直接失败。

这正是它存在的意义：**同一个仓库、同一份源码，换一个编译器就多出一双眼睛**。
