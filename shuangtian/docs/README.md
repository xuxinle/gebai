# 霜天文档地图

**哪份文档答哪个问题、它还跟不跟着代码变。**

> 这份地图是**入口**：除了它自己，其余 18 份文档都在下表中。
> 加新文档时同步改这里（见文末「新知识该写哪份」——地图烂掉的根因是只写读法不写写法）。

## 一句话：先按意图找，再按「寿命契约」决定信多少

每份文档标了**寿命契约**——它决定你该怎么用它：

| 契约 | 含义 | 读的人要注意 |
|---|---|---|
| **活** | 随代码同步更新，**当前真相** | 与代码冲突时以代码为准，但文档不一致属缺陷，应修 |
| **实测** | 内容**冻结**在某一时刻（某次实测的原始数据） | 数据仍然有效但**环境相关**；结论可能已被后续改动超越 |
| **记录** | 已落地的设计/修复记录，讲**为什么这么做** | 不要按它改代码（它描述过去）；要改就看它记的边界与代价 |
| **接口** | 被**源码注释按章节号引用**（见下） | **章节号是稳定接口，禁止重编号**——改之前先 grep |

> ⚠ **源码引用 = 硬接口**。以下文档的章节号被 `src/`、`include/`、`tests/` 里的注释直接引用，
> 重编号会静默打断论证链（读者按注释去查，查到的是别的内容）：
> `BACKLOG.md`、`declarative.md`、`PAINT_DIAGNOSIS.md`（各 4~6 处源码引用）。

## 非文档形态的知识（同样要找得到）

知识不只在 `.md` 里。三类"活"的沉淀：

**① 探针与脚本（`tools/`，160 个）**——用途见 [`../tools/README.md`](../tools/README.md)，按用途分：
- **e2e 驱动**（`*_e2e.py`）：控制通道端到端（`gbcode`/`gallery`/`louyue`/`caiyun`/`split_view`/`theme_file`/`input_action`/`visual_assert`/`events`/`framework_gaps`）
- **逆向验证**（`*_reverse_verify.py`）：把修复回退、断言变红——证明测试**真能抓住**缺陷
- **像素/文字量测**（`*_probe.py`、`*_ink*.py`、`text_*.py`）：从截图里量几何与墨量（观感类改动的尺子）
- **诊断探针**（`tools/*.cpp`）：`crash_probe`、`icon_metric_probe`、`icon_ascii_probe`、`make_sample_png` 等
- **文档/结构核对**（`check_docs.py`、`check_includes.py`、`check_selfcontained.py`）

**② 测试即规格（`tests/`，116 个文件）**——每条 `ST_TEST` 的名字就是一条**不变量**。
想确认"某个行为是不是被保证的"，grep 用例名比读文档更准（文档会漂，测试会红）。

**③ 源码注释里的成因**——最靠近代码、最不容易漂的一层。本仓约定：
注释写**为什么**（尤其是"为什么不那样写"），并在注释里给出来源的文档章节号。
查一个反直觉的写法时，先读它的注释，再顺藤摸到文档。

## 写作约定（改文档时守这几条）

1. **数字必须实测**。性能、用例数、断言数、文件数都写"实测值"并注明口径与环境；
   没有实测的宁可写"*未测*"，也不填猜测值（`DESIGN.md` §11 就是这么处理的）。
   **口径不同要写明**（例：用例数有"源码声明 1062"与"实跑 994"两个口径，差在慢用例跳过）。
2. **状态以代码为准，不以计划为准**。写着"待做"却已完成的条目会误导读者——这类漂移
   在本仓库真实发生过（GPU 行曾长期写"⏳ M3+ 待做"而 M1–M6 早已落地；`LOUYUE_CAIYUN.md`
   曾在实现后仍标"代码未动"）。
3. **章节号是接口**。要重编号就得同步改代码注释与其它文档里的引用，先 grep `§` 再动。
4. **教训要保留成因**。只写"要用 A 不用 B"没用；写上"因为 B 会静默给出错误结果"才不会
   被人"顺手改回去"。
5. **区分"设计意图"与"当前实现"**。两者不一致时要显式说明是哪一种，否则读者无法判断该信谁。
6. **仓库根**：路径分两套——本工程（`shuangtian/`）与主仓库（其上一级）。
   写引用时用**带目录名的相对路径**（写作 `docs/<文件名>.md` 的形态），两套基准都能解析；
   不要写没有目录前缀的裸文件名（两套基准下都指向不到）。写法示例见本表以外任何一行
   （都是真实路径；**示例里的占位符会被 `tools/check_docs.py` 当成实引用而报错**——那是
   设计如此：宁可报错，也不要一个查不出来的假路径）。

## 新知识该写哪份

写下来之前先问一句：**这条知识会跟着什么一起变？** 答案是分流的依据。

| 知识的性质 | 写到哪 | 为什么 |
|---|---|---|
| **框架的缺陷/缺口**（该有没有、行为与文档不符） | `docs/BACKLOG.md` 待做段 | 它是唯一权威清单；写完可 `ask` 问是否当场处理 |
| **可复用的方法/纪律**（怎么量、怎么验、怎么避免某类错） | 对应**专题手册**（观感 → `perceptual_changes.md`；跨平台 → `cross_platform.md`；声明式契约 → `declarative.md`） | 方法要成体系才有用；散在提交说明里等于没有 |
| **子Agent 必知的纪律**（何时用、去看哪一份） | 子Agent **提示词** | 只写导引，**不复述**文档内容（两处同义必然漂移） |
| **具体改动的缘由**（这次为什么这么改） | **git 提交说明** | 与代码同生共死；`git log` 就是它的检索入口 |
| **实测数据**（性能基线、对照实验） | `docs/` 下**新开一份实测报告**，并在地图上登记 | 报告要可寻址；写进地图才不会变成孤儿文件 |
| **反直觉的写法**（为什么这里不能那样写） | **源码注释**（就近）+ 必要时文档章节号 | 最靠近代码，改的人一定会看到 |
| **一次性的过程记录**（本次怎么定位的） | 提交说明或 `BACKLOG` 已完成段 | 不要单开文件——孤儿文档是地图腐烂的主因 |

**判断口诀**：写得下（一处）就近写；写得散（多处要引用）才开新文档，**并登记到本地图**。
