# 霜天文档地图

**哪份文档答哪个问题。** 五份文档按"读者的意图"分工，而不是按"内容类型"堆在一起。

## 五份文档各管什么

| 文档 | 回答的问题 | 什么时候看 |
|---|---|---|
| [`README.md`](../README.md) | 它是什么、怎么跑起来、现在支持什么 | **第一次接触**：从零到跑起 gallery |
| [`DESIGN.md`](../DESIGN.md) | 为什么这样设计、接口长什么样、踩过哪些坑 | 改框架；或想知道"这条规则是怎么来的" |

| [`cross_platform.md`](cross_platform.md) | 跨平台会怎么错、提交前逐条自查什么 | 碰系统 API / 路径 / 入口 / 构建时 |
| [`independent_project.md`](independent_project.md) | 怎么用本框架建**自己的**应用工程 | 要写自己的应用而不是改框架时 |

## 写作约定（改文档时守这几条）

1. **数字必须实测**。性能、用例数、断言数、文件数都写"实测值"并注明环境；
   没有实测的宁可写"*未测*"，也不填猜测值（`DESIGN.md` §11 就是这么处理的）。
2. **状态以代码为准，不以计划为准**。写着"待做"却已完成的条目会误导读者——
   这类漂移在本仓库真实发生过（GPU 行曾长期写着"⏳ M3+ 待做"，而 M1–M6 早已落地）。
3. **章节号是接口**。要重编号就得同步改代码注释与其它文档里的引用，先 grep `§` 再动。
4. **教训要保留成因**。只写"要用 A 不用 B"没用；写上"因为 B 会静默给出错误结果（第 N 条）"
   才不会被人"顺手改回去"。
5. **区分"设计意图"与"当前实现"**。两者不一致时要显式说明是哪一种，否则读者无法判断该信谁。
