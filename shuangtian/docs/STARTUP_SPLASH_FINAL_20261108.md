## 一、最终形态（一页）

用户需求逐轮演化，最终形态是：

> **启动时桌面上只悬浮着一个应用的 logo 与两圈脉冲环，没有任何窗口、没有卡片边框；
> 它播多久由真实加载耗时决定；窗口与首帧一起显出来。**

| 维度 | 落地结果 |
|---|---|
| 视觉 | 应用 logo + 三圈交错脉冲环，**无卡片、无窗口边界、无光晕、无扫光** |
| 技术 | `WS_EX_LAYERED` + `UpdateLayeredWindow`（逐像素 alpha），**不开 Acrylic** |
| 时长 | 自适应：界面准备 <350ms 一闪而过；350ms~1.5s 陪着；封顶 1.5s |
| 启动期窗口 | 缩成卡大小（~340×322 逻辑），恢复尺寸时**先藏再改再显** |
| 代价 | 上屏 19ms → **1.1ms**（画布 6.8MP → 0.15MP）；总启动 948ms（与基线持平） |
| 画布分配 | 4 次 → **3 次**（建窗即铺到工作区） |

## 二、被推翻的方案：Acrylic 磨砂（必须知道为什么）

第一版做的是「磨砂玻璃卡」——Acrylic 背景模糊 + 半透明白卡。**它在实机上永远显示成一块灰白方块**，
排查了很久才发现是两条独立原因叠加：

### 2.1 原因一：DWM 不知道这是暗色窗口

本机系统是暗色（`AppsUseLightTheme=0`），但采样到的窗口是 `(243,253,253)` 纯白。
根因：Win11 legacy Acrylic 的**基础材质色取自窗口框架深浅**，而 `DWMWA_USE_IMMERSIVE_DARK_MODE`
没设时 DWM 一律按亮色窗口处理 → 暗色主题 + 亮色玻璃 = 白板。

**这条也把我设的 `policy.gradient_color` 深色染色完全冲掉了**——看起来像"设置没生效"。
修法是先 `DwmSetWindowAttribute(hwnd, 20, &TRUE, 4)`（19 是 1809~1903 旧属性号）再开 Acrylic。

### 2.2 原因二：Acrylic 是整窗材质（不可绕过）

即使修好暗色框架，Acrylic 仍会**铺满整个窗口**：画布 alpha=0 的区域照样有玻璃层。
用户要的是"只看到悬浮的动画"，所以 Acrylic 本质上不可用。

实测对比（`tools/backdrop_level_probe.cpp`）：

| 档位 | 窗口角像素 | 与桌面一致 | 读法 |
|---|---|---|---|
| Acrylic 开 | `#1E1E20` | **否** | 一块可见方块，卡在里面 |
| Acrylic 关（纯分层） | `#15151A` | **是** | 只有卡悬浮在桌面上 |

**结论：启动卡走纯分层，不开 Acrylic。** 用户确认接受"失去背景模糊"这个代价。
`Backend::set_backdrop_blur` 能力保留（通用窗口能力），但启动卡不再调用。

## 三、纯分层通路的四条硬约束（每条都踩过）

### 3.1 不能用 `rotate_bgra_row` 上屏

它末尾是 `| 0xFF000000U`——把 alpha 强制成不透明。GDI `BitBlt` 不认 alpha，必须全不透明，
**那是它存在的理由**；而 `UpdateLayeredWindow` 要的正是真实 alpha。用它的后果是整窗被当成
100% 不透明，屏幕上一片纯色，**而 `UpdateLayeredWindow` 返回成功**——不看像素根本发现不了。

正解：`dst = (src >> 8) | ((src & 0xFF) << 24)`（保留 alpha 的循环移位）。

### 3.2 必须**逐行写满** DIB，不能"只写非空行"

曾经按"源行是否全空"跳过写入（省拷贝）。**那是错的**：DIB 是**保留型**的，
里面还留着上一次 `fill_dib_with_matte` 写的 `FF1F1F28`（alpha=FF）。
跳过那些行，等于把旧的不透明像素当成"最新的空像素"交给 ULW。

诊断证据：`启动卡诊断：ULW 位 510x483 · DIB 边中 FF1F1F28`（alpha=FF）——
修完后是 `00000000`。**ULW 无法区分"没写"与"写了 0"，所以必须在矩形内逐行写满。**

### 3.3 `WM_PAINT` 重贴路径不能走 GDI

系统启动期至少发 2~3 条 `WM_PAINT`。如果它的重贴路径用 `BitBlt`（不认 alpha），
哪怕 `refresh_early()` 先贴对了，也会立刻被涂成不透明。

判据要从"是否开磨砂"改成"**窗口是否分层**"——启动卡现在只分层、不磨砂，
所以判据换成 `layered_window()`。这个判据散在三处（`show_early` / `refresh_early` / `blit`），
漏一处就一半不生效，**已收成一个 helper**。

### 3.4 磨砂/分层必须在 `ShowWindow` 之前开

先显普通窗口再转分层，Windows 会把显窗那一帧的重定向表面当成初始图层，
后续 ULW 的逐像素 alpha 被当成**整窗一个 alpha**。顺序：`设分层 → ShowWindow → ULW 送内容`。

## 四、启动期小窗（"只露卡"的物理前提）

磨砂/分层都是**整窗**概念，要"只看到卡"就必须让**窗口本身就是卡的大小**。

### 4.1 流程

```
建窗（真实尺寸）→ 缩成卡大小（~340×322）→ center_window
→ set_layered_present(true) → show_early()
→ 泵动画帧（泵点插在 render_frame 的 layout() 之后）
→ resize_hidden_for_startup(真实尺寸)   ← 先藏再改，用户看不到变大过程
→ render_frame()（画完整界面）
→ show_when_ready()（露面）
```

### 4.2 为何必须"先藏再改"

实测（用户截图发现）：直接用 `set_size` 的后果是

| 时刻 | 窗口 | 屏幕 |
|---|---|---|
| 251ms | 671×644 卡 | 卡 ✓ |
| **458ms** | **3533×1922** | **整片纯白** |
| 3006ms | 3533×1922 | 仍然纯白（首帧要 366ms） |

即"卡 → 一眨眼变全屏白板 → 白板停 366ms → 内容才出来"，比不做启动卡还难看。
修法：`resize_hidden_for_startup()` = 先 `SW_HIDE` → 改尺寸 → 画首帧 → 由 `show_when_ready` 再显。
修后实测 `156ms 卡 → 406ms 隐藏 → 523ms 完整界面`，白板一帧都不出现。

⚠ 隐藏后**必须复位 `shown_`**，否则 `show_when_ready()` 会走幂等分支（只补 present），窗口永远出不来。

## 五、动画：从"静态一帧"到"自适应"

### 5.1 曾经退化成静态图，账算错了

上一版只在启动期画**一帧**静态卡，理由是"动画净增 340ms"。那个账算错了：
它测的是**"跑完动画再画首帧"**（动画串行排在首帧前面）。

而首帧那一整块计算（字体首次光栅化 + 图元缓存建表）期间，**屏幕本来就是静止的**——
动画帧可以从这段时间里借。

### 5.2 `SplashPump` 与泵点

新增 `SplashPump`（`include/st/app/splash.hpp`）+ 在 `render_frame()` 的
`layout()` 之后插泵点。为何是那个位置：`layout()` 跑完时画布上还是**卡**（界面还没开始画），
重画卡不会与任何东西冲突。**`paint` 之后不能泵**——那时画布上已是界面内容。

`tick_forced()` 忽略帧率门限，专供"只有几次机会"的启动期。

### 5.3 自适应：跟着真实等待时长走

`ST_SPLASH_MS` 曾是"最长时长"（到点强行切走），现在语义是**最短**；常态下由自适应决定：

| 界面准备耗时 | 行为 |
|---|---|
| < 350ms（常态） | 只播小窗阶段那几帧——**一闪而过是对的**，本来就快 |
| 350ms ~ 1.5s | 播到界面就绪 |
| > 1.5s | 封顶 1.5s（一个完整脉冲周期 1.15s，多了不增加信息） |

记忆落盘在 `%TEMP%/st-splash-<app>.txt`（纯启发值，丢了最坏是下次按冷启动估计 500ms）。

### 5.4 ⚠ 口径错了三次（这是本节最重要的部分）

量"用户看卡多久"时，我连续选错三次判据：

| 判据 | 量到 | 为什么错 |
|---|---|---|
| `now - started_ns` | 883 → 1277ms **递增** | 把动画自己播的时间也算进去 → 正反馈恶化 |
| `render_frame()` 耗时 | **5ms** | 那是"画一帧"，不是"等多久"，差两个数量级 |
| 直接量 `show_early → show_when_ready` | 735 → 964 → 1175 → 1422 **递增** | 同样含动画自身时间 |
| **减去 `splash_anim_ms`** | **稳定 200/480ms** | ✅ 正确 |

**正反馈的机理值得记住**：测"用户在等多久"时，任何被测量动作本身要花的时间都会进入读数，
于是"播得越久 → 量到越久 → 下回播更久"。**减法拆开是唯一出路**：

```
卡在屏时长 = 动画耗时 + 界面准备耗时   →   界面准备 = 卡在屏 − 动画
```

### 5.5 顺带纠正一个长期误读

`perf` 里的 `first_frame 375ms` 一直被当成"绘制耗时"，实际是**里程碑之间的整段**
（含 `show_early`、磨砂开关、尺寸调整）。真正的 `render_frame()` 只要 **5ms**。

## 六、观感细节：为什么最后只剩"logo + 环"

用户逐轮否掉了四层东西，每层的理由不同：

| 层 | 为什么去掉 | 判据 |
|---|---|---|
| 卡片本体（17% 白圆角矩形） | 在透明背景上就是一块可见矩形——用户要"不要卡片边界" | `SplashState::transparent_outside` |
| 内描边（1.5px 强调色） | 它本身就是一圈边界 | 同上 |
| 柔光晕（8 层外扩） | 在透明背景上是一圈可见轮廓 | 同上 |
| 扫光带 | 几何是卡的圆角内接矩形，没有玻璃卡就是一块会飘的白条 | 同上 |
| 品牌标记（菱形套菱形） | 用户："这个图标太丑"——没有任何可识别的意象 | 换成六角雪花（候选对比见 `tools/brand_probe.cpp`） |

**品牌标记的优先级**（用户定的规则）：有应用自己的 logo 就用应用的（`window_icon_png`，
与任务栏同一个文件），没有才画霜天六角雪花。
logo 解码加地址键缓存（原先每帧重新 PNG 解码，实测 3.5ms/帧）。

图标居中：原先画在卡高 **30%** 处（早期给"下方放应用名"预留的位置），
现在卡里只有图形，所以改到**卡的正中心**，卡片比例 1.16 → 1.06（接近方形）。

## 七、量具教训：截图在分层窗口上是废的（踩了两次）

排查"动画是不是没动"时，截图采样显示**每一帧中心都是纯黑 `(0,0,0)`**、diff 恒为 0，
我据此判断"泵没被调用"。**结论是错的——错在量具**：

> 磨砂/分层窗口走 `WS_EX_LAYERED` + `UpdateLayeredWindow`，
> **`GetDC` 抓到的是重定向表面的黑**，不是实际合成结果。

这个坑我自己写在 `tools/splash_probe.cpp` 的注释里、又踩了第二次。

**正确量具**：离屏画布验证（`tools/splash_anim_probe.cpp`）——直接调 `paint_splash_card`
在时间轴上画 8 帧，逐对比较像素差异。判据三条：① 相邻帧必须有可见变化（>200 像素）；
② 变化必须落在卡内（卡外应为全透明）；③ 不能大到像"整块闪"。

## 八、其他修掉的真缺陷（都不在启动卡本体上）

| 缺陷 | 症状 | 修法 |
|---|---|---|
| **DWM 不知道是暗色窗口** | 暗色主题下 Acrylic 是白板 `(243,253,253)` | 先设 `DWMWA_USE_IMMERSIVE_DARK_MODE` 再开磨砂 |
| **`--theme dark` 静默失效** | `xiangqi --theme dark` 实际应用 light，**无任何告警** | `cli.cpp` 里 `--theme` 同时设 `theme_name`（判据用的是 `theme_name.empty()`） |
| **启动底色硬编码** | `0xF7F7FA` 写死，暗色主题启动白闪 | `Backend::set_window_background` 跟随主题 |
| **启动卡窗口没置顶** | 被前台终端/编辑器压住，环像被"裁掉一半"（用户截图） | `show_early` 用 `HWND_TOPMOST`；`show_when_ready` 里撤销 |
| **首帧后无条件 `render_frame()`** | 启动卡刚贴上就被完整界面盖掉（GDI 不认 alpha → 不透明） | 小窗档跳过，恢复尺寸后再画 |
| **GPU 换型抢走画布** | 动画第 12 帧起卡消失，帧数与日志全正常 | `pause_deferred_upgrade`（泵在构造里暂停、析构恢复） |
| **`ST_SPLASH_MS` 用 cmd 传不进去** | `cmd /c "set X=1 && app"` 里 `%X%` 不展开 | 文档改用 PowerShell：`$env:ST_SPLASH_MS="25000"; .\app.exe` |

## 九、建窗一次到位（画布分配 4 → 3）

旧路径（实测日志逐行）：

```
1920x1080   按请求尺寸建窗
3533x1921   fit_work_area 铺开（重分配 27MB）
510x483     启动期小窗
3533x1922   恢复真实尺寸
3533x1922   GPU 升级换设备（不可避免）
```

前两次可合并：工作区尺寸在**建窗之前**就能算（`MonitorFromPoint` + `rcWork`，不需要窗口存在）。
新增 `WindowOptions::fill_work_area_on_create`，建窗直接就是目标尺寸。

**两个坑**：
1. `rcWork` 是**物理像素**而 `logical_width_` 是逻辑像素——忘了除 scale 会导致窗口物理宽 5300（超屏）；
2. 建窗前拿不到 `GetDpiForWindow`（要窗口），改用屏幕 DC 的 `LOGPIXELSX`。

**收益诚实记录**：总启动中位 948ms，与改前**持平**——省下的那次 27MB 分配在噪声范围内。
但路径更干净（少一次无谓分配与重绘）。

为何做成可选开关：建窗尺寸是"黑框/白闪"历史缺陷高发区。开启后做了真窗口验证：
`363ms 小窗有卡（中心 161）→ 865ms 全尺寸深色界面（中心 21,21,26，非黑非白）`，截图无黑框。

## 十一、还没做的

1. **动画全程流畅**：首帧那 300ms 里泵点只拿得到 1~2 次机会（主线程被占满），
   所以启动期是"动几下 → 短暂停顿 → 完整界面"。要做到全程 60fps 得把首帧拆成可中断分段
   （字体预热/排版/绘制/建表），那是另一个量级的改动。
2. **非 win32 平台**：`set_layered_present` / `set_backdrop_blur` / `show_early` /
   `resize_hidden_for_startup` 在 x11/wayland 都是默认空实现——
   那些平台**不会**出现启动卡（不是坏了，是没接）。
3. **应用侧启动打点缺口**：`log_startup_summary()` 只在 `Application::run_loop()` 里调，
   而 gallery/相期/裁云/gbcode 都自己写主循环（只有 gallery 补调了）。
