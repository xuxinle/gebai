# 三维渲染能力：对标 Blender 的差距与路线

> 目标：把 `st::raster::Scene3D` 从「能画透视立方体」建成「能出片的渲染器」，
> 并让**脚本可以直接描述整个三维场景**（AI 原生：不碰 C++ 就能用）。
>
> 参照 Blender（`source/blender/gpu` 的着色器组织、`intern/cycles/kernel` 的
> 材质数学、Principled BSDF 的参数语义），**只取参数语义与数学定义，不搬代码**
> （许可不同；且 Cycles 的路径追踪对实时预览是负优化）。

三条腿：接口 `include/st/raster/scene3d.hpp`（159 行）、软件渲染

## 二、三个阶段（严格按序）

### 阶段 1 · 渲染正确性（不做它，后面全是把错误放大）

| # | 能力 | 状态 | 为什么必须先做 |
|---|---|---|---|
| 1.1 | **线性 ↔ sRGB 转换** | ✅ **已完成** | 现在把线性光照值当 sRGB 直接存。结果是**画面整体偏暗**（实测平均线性亮度 0.055 vs 正确值 0.250，相差 4.5 倍） |
| 1.2 | **色调映射** | ✅ **已完成** | 现在 `clamp01` 先截断。高光、日光、自发光全部糊成一片白，做 PBR 也没用 |
| 1.3 | **背面剔除** | ✅ **已完成** | 现在负面三角形也画。闭合物体从某些角度看会露出内壁 |
| 1.4 | **alpha 混合 + 深度排序** | ✅ **已完成** | 透明物体现在非黑即白 |

#### 1.1 / 1.2 实测结果（`tools/scene3d_color_probe.cpp`）

同一场景（中灰球 + 深灰底），旧行为 vs 新输出链：

| 指标 | 旧（线性值当字节） | 新（ACES + sRGB） |
|---|---|---|
| 平均 sRGB 亮度（屏幕上） | 0.217 | 0.508 |
| 平均**线性**亮度 | 0.055 | 0.250 |
| 过曝像素占比 | 0.0% | 0.0% |

**旧行为把画面压暗了 4.5 倍**（线性域）。图上可见：旧的球发暗发闷、暗部细节丢失；
新链有完整明暗过渡。

> ⚠ **已知遗留**：ACES 对中等亮度（lit≈0.3~0.6）抬得较多，
> 新链整体偏亮、球体几乎接白。下一步应提供“曝光与算子的成对默认值”，
> 或在材质层加入 `base_color` 的 sRGB→线性转换（现在顶点色被当线性用）。

#### 已修：顶点色 / 纹理的 sRGB 解码（2026-10-23 第二轮）

上一轮遗留的“整体偏亮”真因不是 ACES，而是**入口没解码**：
`Mesh::to_unit` 只做 `/255`（注释却写着“线性色”），于是 sRGB 0.55 被当线性 0.55 用
（正确应是 0.26，偏差 2.1 倍），再叠 ACES 的抬亮就接白了。

修正后（同一探针，中灰球）：

| 指标 | 修正前 | 修正后 |
|---|---|---|
| 平均 sRGB 亮度 | 0.508 | **0.451** |
| 平均线性亮度 | 0.250 | 0.178 |

图上可见：球体从“发亮的塑料”变成有哑光质感与完整明暗过渡。

**修改点**（都在入口，不在着色）：
- `mesh.cpp` 的 `to_unit` 改为 `srgb_to_linear`（`colored_sphere` / `colored_box` /
  `plane` / `textured_*` 全部走它）；
- `software_scene.cpp` 的纹理采样同样解码；
- `platform_d3d11.cpp` 的 HLSL 同步（两条腿必须一致）。

**回归测试**：`tests/raster_mesh_color_space_test.cpp`（7 条）+
`scripts/verify_mesh_color_reverse.py`（2 条回退均被拦住）。

#### 口径约定（写入接口需要，见 BACKLOG）

| 位置 | 口径 |
|---|---|
| `math::Color` 入参（`colored_sphere` 等生成器） | **sRGB 字节**，内部解码 |
| `Mesh::vertices` 直接写 | **线性值**，**不做解码**（写入者负责） |
| 纹理 RGBA8（`set_texture`） | **sRGB 字节**，渲染时解码 |
| `begin_frame(clear_color)` / `Lighting` 颜色 | **线性值** |

注：`vertical_shade` 会给顶点色乘 1±0.12，所以白球的顶点色峰值是 **1.12**（HDR），
不是 1.0——这是设计如此。

#### 1.3 / 1.4 实测结果（2026-10-23 第三轮）

**背面剔除**（`CullMode`：None / Back / Front，默认 **Back**）。
方向用**单面平面**验证（封闭实体分辨不出方向对错）：

| 剔除模式 | 正面可见 | 背面可见 |
|---|---|---|
| None（双面） | 37636 | 37636 |
| Back（剔背面） | 37636 | **0** |
| Front（剔正面） | **0** | 37636 |

两条腿完全一致（`tools/scene3d_cull_probe.cpp`）。

**透明混合**（`Material::opacity`，<1 时进透明队列，远→近排序）。
同一个半透场景：

| | 中心像素 | 混合发生的位置 |
|---|---|---|
| 软件腿 | (178,184,62) | **线性空间**（解码已画像素 → 混 → 再编码） |
| GPU 腿 | (118,121,53) | 渲染目标上的**已编码 sRGB 值**（D3D 固定功能混合的标准行为） |

两者都对，只是不在同一个空间——所以判据钉“绿透出来了”这种定性事实，不钉具体字节。

#### 第三轮踩到的四个坑

1. **GPU 腿的 `set_material` 原本是空实现**（基类空实现 + GPU 未 override）。
   后果：同一场景软件腿半透明、GPU 腿全不透明，**且不报错**。
   实测：`ST_SCENE3D_BACKEND=software` 的用例全过，设成 `gpu` 则中心像素是纯红。
2. **GPU 只有一套固定写深度的状态**，透明物体必须“只测不写”（否则后面的透明面被挡住）。
   已加 `depth_no_write` 并与 `Material::depth_write` 对齐。
3. **量背景不能拿传入的清屏色**：它现在经 sRGB 编码，画布里的值不等于传进去的值
   （实测 0x14 → (84,95,119)）。拿原值当背景 → 全屏都算实体，三种剔除模式读到同一个数。
4. **测试自己的量尺不具备分辨力**：`software_scene_renders_a_cube` 原来靠
   “绕 Y 轴转 6 个角度看**平均**亮度”验证面间差异——而立方体四个侧面轮流出现、
   光照固定，平均值本来就不变（实测极差 **1.46**）。它在改动前能过，靠的是
   “背面也画”带来的噪声。已改成**单帧内比三个可见面**（顶/正/右：94.4 / 112.5 / 94.4）。
   同类修正：`depth` 与 `perspective` 两条的背景基准都改为“左上角实际值”。


1. **清屏色没走输出链**：`begin_frame` 直接 `canvas_.clear(clear_color)`，
   于是背景是旧行为、实体是新行为——**一帧里混了两种色彩空间**，深灰底渲染出来一片白。
2. **`begin_frame` 重置 `lighting_` 时没同步 `tone_map_`**，导致算子慢一帧。
3. **探针写 PNG 时字节序搞错**：画布像素是 `0xAARRGGBB` 且**已预乘**，
   按 `0xRRGGBBAA` 展开会让蓝通道恒为 255（图一片蓝，而统计量却在正常变化）。
   必须经 `math::unpremultiply`。


### 阶段 2 · 渲染表现力（对标 Blender 的观感）

#### 2.3 / 2.4 实测结果（2026-10-23 第四轮）

**多光源**（`Lighting::extra_lights`，最多 3 盏附加平行光）——球体逐档加光：

| 布光 | 亮面 | 暗面 | 暗/亮 | R | B |
|---|---|---|---|---|---|
| 仅主光 | 184.8 | 126.8 | 0.686 | 126.3 | 131.4 |
| +补光 | 189.8 | **174.2** | **0.918** | 173.6 | 178.3 |
| +轮廓光 | 190.8 | 174.2 | 0.913 | 173.6 | 178.3 |
| 暖色补光 | 191.8 | 171.6 | 0.895 | **180.1** | **160.0** |

三条判据成立：补光把暗面抬 47.4（暗/亮比 0.686 -> 0.918）；轮廓光影响亮面边缘
（189.8 -> 190.8）；暖色补光产生色相偏移（R 比 B 高 20.1）。

**平面投影阴影**（`PlanarShadow`）——强度四档：

| strength | 地面区 | 球体上方 | 阴影区 |
|---|---|---|---|
| 0.00 | 135.4 | 201.4 | 137.9 |
| 0.25 | 135.4 | 201.4 | 77.8 |
| 0.45 | 135.4 | 201.4 | 41.7 |
| 0.70 | 135.4 | 201.4 | **12.2** |

地面与球体两处恒定不变、阴影区单调下降 125.7，说明阴影既生效又**没有盖到投阴影体上**。

#### 阴影的三个坑（全部是「代码看起来对、画面就是不对」）

1. **方向判反**：`key_direction` 是「指向光源」，光从上方来时 `dir.y > 0`。
   写成 `if (dir.y >= -1e-4f) return`（要求光从下方来）-> 一个三角形都不收集。
2. **深度竞争**：阴影与地面共面，实测 `shadow_z=0.9619 > ground_z=0.9502`，
   于是 `z >= depth` 恒成立，**零像素被改**——而三角形收集（784 个）与绘制调用
   全都正常执行。调 `lift` 是在与浮点精度搏斗，不是解决问题。正解是**实体遮罩**：
   实体写像素时标记，阴影只在未标记处画。
3. **采样点猜错**：探针把阴影采样点定在 (232,300)，而实际阴影重心在 (146,249)：
   四档读数完全一样，于是误判成「阴影未生效」。后来改用**逐像素最大差异**当判据，
   不再依赖采样点。

#### GPU 腿的阴影：**未实现，但不再静默**

GPU 腿会保留 `PlanarShadow` 参数但不渲染。测试里用 `backend_lacks_shadow()` 显式跳过
（而不是让它失败——那会把「未实现」与「回归」混为一谈）。
这是从 `set_material` 那次学到的：**静默忽略比未实现更贵**。

#### 2.1 / 2.2 实测结果（`tools/scene3d_material_probe.cpp`）

五种材质，同一中调灰球（480×480，软件腿）：

| 材质 | 均值 | 峰值 | 高光占比% | metallic | roughness |
|---|---|---|---|---|---|
| matte-plastic | 0.587 | 0.737 | 0.00 | 0 | 0.95 |
| glossy-plastic | 0.590 | **0.783** | 0.00 | 0 | 0.15 |
| rough-metal | 0.142 | 0.369 | 0.00 | 1 | 0.55 |
| polished-metal | **0.086** | **0.970** | **0.22** | 1 | 0.10 |
| emissive | 0.840 | 0.881 | 0.00 | 0 | 0.95 |

三条物理判据都成立：
- **金属失去漫反射**（均值 0.587 → 0.086），这是金属与非金属的分界线；
- **粗糙度控制高光宽度**（rough 0.10 峰值 0.970 + 高光占比 0.22%；0.55 峰值降到 0.369）；
- **自发光抬高整体**（0.840）且被 ACES 滚降（峰值 0.881，不超过 1）。

#### 本轮最贵的缺陷：`Mesh::sphere` 绕序反向

球体的三角形绕序与顶点法线**完全相反**（实测 224/224 反向），而
plane / box 都是对的。这个缺陷在引入背面剔除之前**完全看不出来**——
两面都画，深度测试自己挑出对的那一面。

加上 `CullMode::Back` 后它立刻现形：球只画出**背面**
（实测 `n.z>0.5` 的像素 **0** 个、`n.z<-0.5` 的 **25 万**个），内外翻转。

**而当时全部 1849 条测试都是绿的**——包括专门测剔除方向那条，
因为它只用平面，而平面的绕序恰好是对的。

修复：索引从 `{a,b,a+1}` 改为 `{a,a+1,b}`（两个三角形都改）。
加固：`tests/raster_mesh_winding_test.cpp` 对**每个生成器**单独断言
（不靠一个对的给错的掩护），并带`verify_winding_reverse.py` 逆向验证。

#### 3.1 实现要点（`scene3d_script.hpp/.cpp`）

一份 JSON 描述整个场景，`render_scene` 负责**正确的调用顺序**——这正是本层
存在的理由：过程式 API（`begin_frame` → `set_*` → `draw_mesh` → `end_frame`）
顺序错了会静默失效，而生成代码的模型很难自己发现。

实测（`tools/scene3d_script_probe.cpp`，一份含地面/球/立方体/阴影/暖色补光的 JSON）：

| 判据 | 结果 |
|---|---|
| 字段解析忠实 | 9 项逐个核对全对（fov 42 / ambient 0.18 / ground_y -0.5 …）|
| 错误带字段路径 | 6/6 条含具体字段（`objects[0].shape`、`camera.eye`、`tone_map` …）|
| 参数确实生效 | 改 `metallic` 0→1：均值 111.90 → 87.13（差 24.76）|
| 阴影确实生效 | 关阴影：111.90 → 115.40（变亮 3.5）|
| 确定性 | 同一 JSON 渲两次逐像素相同 |

#### 3.1 踩到的真 bug：地面被当成实体

`render_scene` 原本先 `set_planar_shadow` 再画所有对象。平面投影阴影的契约是
「设阴影**之前**画的不算实体」——于是地面被当成实体打上遮罩，**阴影一个像素
都画不出来**（实测：开关阴影均值 115.40 → 115.40，完全不变）。

图看着完全正常，只是没有影子——「能渲出图」这条判据在两种情况下都是绿的。

修法：给对象加 `ground` 字段，`render_scene` 分两遍（先地面 → 设阴影 → 其余）。
JSON 里无法表达"先画谁"这种顺序依赖，所以必须显式标记。

逆向验证 `verify_scene_script_reverse.py`：把「顺序反了」与「忽略 ground 字段」
各自放回去，`scene_script_shadow_takes_effect` 都变红。

#### 3.3 为什么错误信息必须带字段路径

这份 JSON 通常是模型生成的。它拿到「解析失败」四个字无法自我修正，
拿到 `objects[0].shape：只接受 sphere/box/plane/cylinder/torus，收到 dodecahedron`
可以立刻改对。所以每个失败点都构造带路径的消息，测试里也逐条断言。

## 三、验收口径（每个能力都要有，不许"看起来像"）

- **探针**：`tools/scene3d_*_probe.cpp`，输出可复算的数（不是"我觉得更好了"）。
- **两条腿一致**：软件与 GPU 必须消费同一组参数与同一个公式
  （`shade_terms` 已经是这个原则，新能力照此办理）。
- **逆向验证**：每个回归测试都要确认"把实现改坏它会红"。
- **不改变默认行为**：老场景（没设新参数）必须逐像素不变——这是渐进采用的底线。

## 六、逆向验证踩到的三个真问题（都是“测试本身不可靠”）

1. **连续性测不出“退化成纯幂函数”**：幂函数本身处处连续。真正区分两者的是**暗部斜率**
   （分段线性段 12.92 vs 幂函数 ~3~5）。所以加了一条专门量暗部斜率的用例。
2. **ACES 系数错 0.36 测不出**：“与 Filmic 差 >0.01” 的阈值比错误量小。
   改成钉 5 个具体参考值（容差 0.004）。
3. **曝光顺序反转测不出**：`None` 档的 `clamp` 与乘法可交换；换成 ACES 后又只断言
   “变大但不到两倍”，两种实现都满足。最终改成钉**输出字节等于正确顺序的值**，
   并额外断言两种顺序的差 >0.01。

#### 3.4 接入裁云 `model3d`：`model_script` 字段（2026-10-23 第五轮）

图层加了一个字段 `model_script`：值是**一整个场景 JSON**（`scene3d_script.hpp` 的格式）。
非空时整幅图层由它描述，与原有的 `model_shape` + `model_*` **互斥**
（原路径是"一个网格 + 图层相机/光照"，场景脚本自带相机与光照，混在一起
会变成"到底用谁的相机"）。

端到端实测（`examples/caiyun/assets/scene-script-demo.json`，1280×720 / 30fps / 6s）：


画面含地面 + 金色球体（高光）+ 粉色金属环（自遮挡）+ 蓝色金属方块 + 三个投影。

#### 3.4 踩到的最贵的一个坑：**导出卡死**

第一版接完，画面看着完全正常（截图对），但**导出卡在 33/180 帧、控制通道完全超时**
（进程还在，什么都不响应）。

根因是两层 `Scene3D::create` 打架：

| 层 | 对 `ST_SCENE3D_BACKEND` 的操作 |
|---|---|
| 裁云 `scene_slot::acquire` | 为了强制软件腿，**临时 `_putenv_s`，用完还原** |
| 我的 `render_scene` | 每次都 `Scene3D::create`，而 `create` **读写同一个变量** |

两者叠加破坏了宿主的保存/恢复。

**修法**：新增 `render_scene_into(spec, scene, canvas, bg)`——复用调用方已有的
实例，不新建、不碰环境变量。`render_scene` 改成"create 之后转发给它"，
两条路径共用同一份渲染逻辑。

**判据也跟着改**：只比两次渲染的像素**抓不到**这个缺陷（内部偷偷 create，
像素照样一样）。改用**标记法**——先在外部实例上画一帧，再调 `render_scene_into`，
断言"外部实例的状态被推进了"。手工把 `render_scene_into` 改回"内部新建"
验证过：`changed > 0` 立刻失败。

#### 3.4 schema 两处必须同改

`model_script` 加进 `Layer` 后，还必须同时改：

- `examples/caiyun/schema.cpp` 的字段表（否则报"未知字段 'model_script'（已忽略）"）；
- `examples/caiyun/layer_schema.cpp` 的属性表（否则界面看不到这个字段）。

`tests/caiyun_layer_schema_test.cpp` 有一条断言"每个 schema 字段都能读写"，
它当场抓到了我第一版的过错：我把 setter 写成"非法 JSON 就拒绝写入"，
而这条不变式要求任意探测值都能写。改法是**setter 原样存**，
把校验推到渲染前（失败画醒目占位 + `ST_LOG_WARN`）——用户编到一半的 JSON
不该被界面拒绝。

按「AI 原生使用」的标准选的六项——都是**不补就没法看**或**补了立刻拉开差距**的。
全部经 `tools/scene3d_blender_probe.cpp` 像素级实测（开关前后差异，不是"看起来像"）。

#### 4.1 为什么 `base_color` 是硬限制

之前颜色**只能来自网格顶点色**：同一份 `Mesh` 想换颜色就得重建网格，
多个物体共用同一份网格时也无法各自上色。加了材质基色后，网格只描述
**形状与 UV**，颜色由材质决定——这正是 Blender 的「物体数据 vs 材质数据分离」。

渐进采用底线：`base_color_set = false` 时**完全沿用顶点色**，老场景逐像素不变。

#### 4.5 AgX 为什么不能逐色道做

ACES / Reinhard / Filmic 都是**逐色道**的 S 曲线：它不知道"这个像素是不是在
色域外面"，所以高饱和亮部会直接冲成纯红/纯绿（俗称"颜色烧焦"）。

实测对比就是铁证——同一个严重过曝的红色发光球：

| 色调映射 | 平均饱和度 | 画面 |
|---|---|---|
| ACES | **1.000** | 纯红一片，亮度层次全丢 |
| AgX | **0.096** | 滚降到近白，仍保留层次 |

AgX 的关键是**先旋转到宽色度空间**（Rec.2020）、在三维里统一压亮度，
所以能保住高光色相。这就是 Blender 4.x 把它设为默认的原因。

实现取舍得说清楚（不假装完整）：只做了 sigmoid 拟合 + 去饱和，
**没有** look（Punchy 等）、**没有**色域映射、对比度固定。

#### 4.3/4.4 踩到的一个真 bug：聚光方向约定反了

`Light::direction` 的约定是「指向光源」（从表面看过去），而聚光锥体是从光源
**射出**的方向。第一次实现时只把一边取反 → 点积恒为 -1 → 锥外判定永远成立
→ **聚光照不出任何东西**（整块画面全黑，看起来像"功能没生效"）。

修法：`cos_angle = -(axis · out.direction)`，两边约定对齐。探针实测从
"中心=0 角落=0" 变成 "中心=185 角落=109"。

#### 4.x 两条路径都必须用 `sample_light`

`shade_terms_at`（无材质时的快路径）与 `shade_surface`（有材质时）是两条独立的
着色路径。第一次只改了后者，结果**没设材质的场景里点光完全不生效**——
探针里点光/聚光四项全红、数值一字不变。这是本仓库反复出现的形态：
一处改了、另一处忘了，而"看起来能用"。
