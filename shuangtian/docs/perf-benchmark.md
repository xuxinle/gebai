# 渲染性能实测与外部对比（2026-10-31）

本文件记录一轮**量化排查**的结论：瓶颈在哪、优化了什么、以及和 Blender
的公平对比。数据全部可在本机复现（命令见各节）。

环境：RTX 4080 SUPER / 驱动 610.88 / Blender 5.2.3 LTS / ffmpeg 8.1.1。

---

## 一、当前性能（1920×1080）

### 真实片子（`examples/caiyun/assets/sample-basic.json`，300 帧）

| worker | 每帧 | 说明 |
|---|---|---|
| 1 | 51.7 ms | |
| 2 | 31.5 ms | |
| 4 | 28.7 ms | |
| 8 | 28.4 ms | **已平坦** |
| 12 | 28.5 ms | 再加无收益 |

**4 路以后撞到串行瓶颈，加资源不再有效。**

### 空场景（0 图层）——性能地板

| 分辨率 | 带统计 | `--no-stats` |
|---|---|---|
| 1280×720 | 14.9 ms | **10.0 ms** |
| 1920×1080 | 26.9 ms | **15.9 ms** |
| 3840×2160 | 109.4 ms | **69.9 ms** |

严格随像素数线性（带统计 ≈13.4 ms/Mpx，无统计 ≈8 ms/Mpx）。
**与画面内容无关**——这是"每帧必须把整幅画面当字节流处理"的固有成本。

### 各环节拆解（1080p，1 worker，`--no-stats`）

| 环节 | 耗时 |
|---|---|
| 渲染（绘制录制） | 23.5 ms |
| GPU→CPU 回读（Copy/Map/memcpy） | 1.6 ms |
| 编码 + 管道 | 19.4 ms |
| **端到端** | **42.9 ms** |

## 二、GPU 到底用了多少

实测（Windows `GPU Engine` 计数器，`tools/gpu_utilization.py`）：

| 指标 | 值 |
|---|---|
| GPU **3D 引擎**平均占用 | **3.34%** |
| 峰值 | 7.84% |
| Copy 引擎平均 | 3.47% |
| CPU（1 worker） | **约 180%**（近 2 核满载） |

**GPU 基本空闲，瓶颈在 CPU。** 原因：每帧要把 8.3MB 像素搬回 CPU
（交给编码器），三维光栅化本身只要 0.84 ms。

## 三、和 Blender 的公平对比

### 对比条件（严格对齐）

1920×1080 / 120 帧 / 单线程 / **纯渲染不含落盘**（双方都不含编码与写盘）/
3 个低细分图元（球/立方体/环）/ 单平行光 + 环境光 / fov 42° / 8× 抗锯齿。

Blender 场景由 `tools/bench_blender.py` 生成。

### 结果

| | 纯渲染 | 备注 |
|---|---|---|
| **霜天** | **24.1 ms/帧** | |
| **Blender EEVEE** | **162 ms/帧** | 三次采样 163.9 / 159.8 / 162.2 |
| 倍数 | **霜天快 6.7×** | |

### 必须说清的三个保留

1. **场景太简单，对 Blender 不利。** 三个低面数图元时，Blender 的固定开销
   （依赖图求值、Python 解释、GPU 上下文切换、着色器编译）占了大头。
   EEVEE 在简单场景上本来就不划算。

2. **霜天的三维能力远不如 Blender。** 22 个内置图元 + glTF/OBJ 导入，
   **无材质节点、无体积、无次表面散射、无运动模糊、无景深**。
   快的一部分原因是**做得少**。

3. **场景变复杂后结论会反转。** Blender 把整个管线放在 GPU 上，
   而霜天每帧回读 8.3MB 到 CPU。面数上万后差距会拉开。

### 结论

「霜天比 Blender 快 6.7 倍」**只在上述特定场景成立，不能当通用结论**。

正确表述：**霜天在"应用内嵌 / 简单三维图层 / 批量出片"这个定位上比 Blender
合适得多**——Blender 光启动与场景求值就要几百毫秒。

复现：
```bash
"C:\Program Files\Blender Foundation\Blender 5.2\blender.exe" \
  --background --factory-startup --python tools/bench_blender.py -- EEVEE 120
```

## 四、"跳过 ffmpeg、自己接 NVENC" 的验证结果：不可行且无收益

### 4.1 技术前提缺失

`tools/nvenc_probe.py` 验证：

```
[OK]   加载 nvEncodeAPI64.dll
[OK]   驱动报告 NVENC API 1.13（原始值 209）
[FAIL] NvEncodeAPICreateInstance 返回 15 (0x0F) —— INVALID_VERSION
```

`NV_ENCODE_API_FUNCTION_LIST` 的**结构布局只存在于 SDK 头文件**
（`nvEncodeAPI.h`）里，本机没有安装 CUDA SDK。动态加载时靠猜字段布局
必然失败——传入 `0x0D000001` 与 `0x000000D1` 均返回 `0x0F`。

### 4.2 即使接通也零收益（这是更重要的结论）

8 worker 真实片子（1080p，`--no-stats`）：

| 配置 | 每帧 |
|---|---|
| 管道 + libx264（当前） | **30.1 ms** |
| PNG 落盘（**不走管道**） | 55.6 ms |
| 软件画布（`CAIYUN_GPU=0`） | 35.4 ms |

**"不走管道"反而更慢** → 编码已与渲染**并行重叠**，不是瓶颈。

worker 扫描也印证：4 路 28.7 ms → 12 路 28.5 ms，**完全平坦**。

换句话说：那 19.4 ms 的"编码+管道"只在**单 worker** 时可见；
批量导出（多 worker）时它已经被藏掉了。跳过 ffmpeg 省不到东西。

### 4.3 结论

**不做。** 需要先下载几百 MB 的 CUDA SDK、再写几百行（含 mp4 封装），
而实测收益为零。

## 五、本轮实际做的优化

| 改动 | 效果 |
|---|---|
| `Scene3D::create` 接上进程级互斥（此前声明了但无人调用） | **修好 4/8 路并行卡死** |
| 导出路径跳过打包回读视图（`skip_next_packed_readback`） | 省 14%（57.7 → 50.0 ms） |
| 画面质量统计可关（`--no-stats`） | 省 **32%**（1080p）/ 37%（4K） |
| 选腿探测改用缩小实例（1/4 边长） | `Scene3D::create` 从 **2100 ms → 9 ms** |

## 六、下一步真正值得做的

**瓶颈是那 28.5 ms 的渲染 CPU 开销**（多 worker 下），不是编码、不是 GPU。

其中已知：三维绘制 0.84 ms，回读 1.6 ms，剩约 26 ms 是绘制录制与像素处理。

优先级（按收益/风险）：

1. **减少每帧全画面遍历次数** —— 中收益、低风险
2. **异步回读** —— 低收益（实测 4-8%）、中风险（历史上有死锁）
3. ~~自接 NVENC~~ —— **已验证零收益，不做**
