# 观感类改动的协同开发手册

> **适用场景**：改动的验收标准是**人的主观感受**（"更清晰了 / 更均匀了 / 更丑了"），
> 而不是测试红绿。典型分支：字体渲染、配色、动画、交互手感。
>
> **为什么单独立一份**：这类改动与普通缺陷修复**根本不是同一种工作**。普通修复有
> 明确的"对/错"，而观感改动的验收标准长在用户身上——**指标上涨不等于结果变好**，
> 而且这个偏差**在聚合指标里往往看不见**。本仓库在 2026-10 的字体渲染任务上，
> 用四次"指标涨了、用户说更差"的返工换来了下面的条目。

---

## 1. 第一原则：用户是验收者，用户的话是**现象**不是**诊断**

用户说"不均匀""不好看""有点糊"——这是**现象**。把现象翻译成可测量、再把测量对回现象，
是开发者的职责。**不要**：

- ❌ 让用户去描述"是哪个参数不对"（他看不到参数，只能看到结果）；
- ❌ 拿一个自己发明的解释去搪塞（实测：开发者把某次数字差异解释为"孤立单字形 vs 文本串"，
  后来用直接实验推翻——两种排布的总墨比只差 ≤0.7%，真因是**两个不同的统计量**）。

**做法**：把现象拆成**可量的正交量**，再用图把量到的差异**指给用户看**，请他确认方向。

---

## 2. 先把"感受"拆成正交量，再建尺子

**反例（本仓库真实代价）**：用户报"中文字体线条粗细不均匀"。开发者把它当成
"笔画没吸到网格"，于是连做三项拟合改进，指标（crisp 锐度）一路上涨，
而用户每次都说"更差了"。

**真相**：把测量拆成两个**正交**量后就明白了——

| 量 | 定义 | 结果 |
|---|---|---|
| 几何宽度 | 笔画横截面的覆盖率之和 | 拟合前后都 ≈ 参照 |
| **墨色峰值/覆盖离散** | 同一字内各墨像素的覆盖率标准差 | 拟合把分布**变成双峰**（吸上的满黑、没吸上的留原相位） |

即"整体更锐"与"彼此更均匀"是**两个问题**，前者盖住了后者的恶化。
**判据要落在"离散/一致性"上，而不是"平均锐度"。**

**可操作规则**：
- 任何"更好"的结论，必须**至少两个正交量同向**才算数；
- 只有一个量上涨时，先问："还有哪个量被我漏掉了？"

---

## 3. 参照必须取**用户实际那条链路**

实测教训：用**无头**浏览器当参照，它不带桌面 GPU 合成，渲染比用户看到的更浅，
据此得出的方向**恰好相反**（并被用户当场驳回）。

参照要包含用户侧的**全部变量**：主题（亮/暗）、DPI、字体族与版本、硬件合成路径、渲染模式。

> 本仓库的落地：A/B 对照用**真窗口**浏览器 + Xvfb（非 headless），并用 CDP 导出
> **逐行实际字体归属**做同源断言——否则量到的是字体差异而不是渲染差异。

---

## 4. 报告数字时**必须注明统计量**（最容易翻车的一处）

同一批数据，两个统计量可以给出**方向相反**的结论：

| 统计量 | 含义 | 对"少数明显异常的字形" |
|---|---|---|
| 逐字形比值的**中位数** | 典型字形的表现 | 敏感 |
| **总墨量之比** | 整体浓淡（对应观感） | 被大字形稀释 |

实测：同一批字母，中位数口径是 0.92、总墨量口径是 0.96，差 4%——
开发者为这个差编了一个假解释（见 §1），又花了半天实验才推翻。

**规则**：
- **主口径用"总墨量之比"**（它对应整体观感），中位数作为**离散度**指标并列报出；
- 报数一律写成"X（口径：总墨量比 / n=…）"，不留裸数字。

---

## 5. 量尺本身的三个坑（都实测踩过）

### 5.1 模式必须与参照一致

用**灰度**渲染去比**亚像素**的参照 ⇒ 墨量差 5%，而那是模式差不是质量差。
（同理：滤波 vs 未滤波、sRGB vs 线性，都是模式。）

### 5.2 切窗口的口径要足以容纳被测特征

- **太紧**：用"紧凑 DOM 行框"切窗口会**裁掉最宽那笔**——汉字 `三`（三横、最下横最宽）
  在 32px 下被测成 38px 宽而参照 42px；改用"相邻行框中点"的大窗口后同一批数据从
  "0.929" 变成 "0.992"。
- **太松**：大字号下大窗口会**吃到邻行的墨**——32px 档窗口 ~70px 而字形墨高 ~45px，
  实测包围盒高度从 45 变 70，那一档的数整批不可用。

⇒ 窗口必须是"**只含本行、且不小于本行墨迹**"的区间；字号跨度大时要分别校验。
大字号的逐字形量测需要**墨迹连通域隔离**（本仓库当前工具未做，因此大字号不报逐字形数）。

### 5.3 探针的文件名必须可区分

多个档位写同一个固定文件名 ⇒ 后跑的静默覆盖前一个，量出来的是**上面那一档**的数据
（实测：用 `--nofit` 的探针把默认档的图覆盖了，导致一批数偏低 3%）。

---

## 6. 一条假设一条实验；失败就回退

把多个改动捆在一轮里，失败时**无法归因**。实测：三项拟合改动里两条单开无效、
一条完全无效——只有拆开才看清。

回退要回到**能重建的状态**（git 提交），而不是"把改动手动改回去"。

---

## 7. 改默认值 = 改所有应用的观感 ⇒ **必须先问用户**

默认值是**产品决策**，不是实现细节。

**做法**：给出**候选 + 实测差异**，让用户选；选完把决策依据（数字）写进代码注释，
让下一个人知道这个值的边界在哪。

**并且**：把"应用默认档"抽成**可被测试引用的常量**（本仓库是 `st::app::ClassGammas`
+ `apply_class_gammas()`），测试与实现走**同一个入口**——否则会出现
"探针里改好了、应用里没生效"而测试全绿的情况（**实测漏接过一次**：
某个档位只写进了渲染器与探针，`app.cpp` 当时没接）。

---

## 8. 结论与观感冲突时，**先怀疑尺子**

用户说"更差了"而指标在涨 ⇒ 优先检查：口径漏了哪个正交量？参照对不对？统计量选得对不对？

**本仓库的四次返工，每一次"更差了"都对应一次口径缺陷，而不是用户看错。**

---

## 9. 一次可复用的协同循环（本仓库跑通的形态）

```
① 复现：在**用户实际配置**下渲染出图（主题/DPI/字体都要对）
② 分族：同一批内容按**可归因的维度**拆分（字符类 / 字号 / 笔画形态），
        不要混在一行里量——混排会让差异无法归因
③ 建尺：至少两个正交量 + 注明统计量；先验证"量尺自己能分辨已知差异"
④ 归因：逐字形/逐档二分（开/关某机制），得到"差距来自哪个机制"
⑤ 修：一条假设一条实验；改动落到某个**类/档**上（而不是全局）
⑥ 验证：**逆向验证回归**（把修复回退，测试必须变红）+ 全量测试 + lint
⑦ 出图：把改动的**前后 + 参照**三方并排给用户，标上实测数字，请他确认
⑧ 定默认：给候选与数据，由用户拍；拍完写进注释与 BACKLOG
```

## 10. 反模式清单（出现任一即停手自查）

| 反模式 | 为什么危险 |
|---|---|
| 只用**一个**聚合指标就宣布"更好了" | 它可能同时藏着另一个正交量的恶化 |
| 拿"测量手段本身"当参照 | 参照与用户链路不一致时，方向会反 |
| 为两个数之间的差异**编解释**而不做实验 | 实测编过一次，是错的，还白花半天 |
| 直接改默认值 | 那是全应用的观感决策 |
| 交付"恒绿的回归测试" | 它看起来像护栏，实际什么都拦不住 |
| 把多个改动捆一轮 | 失败时无法归因 |
| 相信逐字形尺度的"实心像素比" | 单个字形的满黑像素只有几十个，差 1 像素就是几个百分点 |
| **把用户两次反馈当成一个量在调** | 它们常是**两个独立量**；调一个必然破坏另一个（§11） |
| **发现两处不一致时挑一边迁就** | 不一致只说明"至少一个错"，挑错方向会把对的改坏（§12） |
| **让墨迹判据吃到半透明叠绘的边缘** | 光标/阴影/焦点环的边缘不是纯色，会被当成墨迹（§13） |

## 11. 把反馈分解成量：用户说的是**一个**问题还是**两个**？

这是本仓库最贵的一课（2026-10-07，代码编辑器行盒，连读四报返工）。

### 四个报、三个量

| 用户报 | 我当成 | 真正该动的量 |
|---|---|---|
| 「行间距全在行下方」 | 行盒内文字位置 | **文字在盒里的位置**（增量只堆下方） |
| 「背景和光标还是偏下」 | 同上（一个量） | 同上（这一报确实是同一个量） |
| 「上部的背景和光标怎么没了」 | 以为还是"文字位置" | **带的范围**（我把带缩短了，另**一个**量） |
| 「注释没有在行背景垂直居中」 | 以为还是"带的范围" | **基线的一致性**（中文/拉丁被排到不同基线上） |

**第二报与第三报是一对**：它们不矛盾，而是一个共同解的**两个侧面**。
第三报的真正成因是——我用"改带的长短"去治"文字偏下"，
于是保住了文字、却破坏了带。**两个量只能用两个动作分别修。**

### 判据：怎么知道是几个量

拿不到用户意图时，用**几何上互不蕴含的测度**去卡：

```
同一现象："文字在带里看起来偏下"
  量 A：文字墨迹中心 vs 带中心        → 文字位置
  量 B：带高 vs 墨迹高（带的完整性）  → 带的范围
  量 C：多个 token 的"底"是否共线      → 基线一致性
```

A 成立推不出 B（文字居中而带很矮），B 成立推不出 C（带完整而中英文错底）。
**互不蕴含 ⇒ 必须分开量、分开改。**

### 实测数据（那些数字值得记住）

| 对象 | 读数 | 说明 |
|---|---|---|
| 拉丁行墨迹中心占行盒 | **28%** | 拉丁视觉重量在 x-height |
| 中文行墨迹中心占行盒 | **46~52%** | 中文是方块字、重心居中 |
| 两者差 | **4.2px** | ⇒ **一个位移不可能同时让两侧居中** |
| 行带 22.77 vs 缩后 15.07 | 差 **7.7px** | 缩带把行距变成了"带与带之间的缝隙" |
| 中文 vs 拉丁 ascender | 15.87 vs 11.14 | 差 **4.7px** ⇒ 逐 token 落基线时中文比拉丁低 4.7px |

**发现 A/B 差很大（28% vs 46%）时，不要去调一个"折中位移"**——
那是把两个量压成一个，两边都不会满足。应当**换口径**：不再问"文字在带里的位置"，
而是让**带贴合文字**（带高 = 字体 em 盒），两个量的矛盾就消失了。

### 反模式

> "用户又来说更差了，我把上次改动的那个量往回调一点。"

调参数前先问：**这次他看的是不是我上次动的那个量？** 若不确定，重新测一遍。

## 12. 两处不一致时：先判定哪个对，再统一

**不一致只说明"至少一个错"，不告诉你该往哪边改。**

实测（2026-10-07，同一个编辑器的行盒）：几何侧与绘制侧各用一个"基线"量，
于是"几何说已居中、屏上偏 6.6px"。我的第一反应是把**几何去迁就绘制**——
方向反了：真正错的是绘制（它按 token 字符集落基线，中文与拉丁不同底）。

**正确顺序**：

1. 把两个量都量出来（哪个是 A、哪个是 B）；
2. 问"**这个量本质上应当是什么**"：基线是"**行的**属性"还是"**token 的**属性"？
   ——答案是行属性 ⇒ 按 token 算的那一侧是错的；
3. 把**错的那侧**改成对的，再断言"两侧一致"。

**自检**：如果你写的回归只断言"两侧相等"，它**抓不住"两边一起错"**。
要另外断言"这个量本身满足它应有的语义"（如"中/拉丁/混排的基线必须同值"）。

## 13. 量尺的读取污染（都实测踩过）

前文 §5 讲的是"**窗口**取多宽"，这里讲"**取到的像素算不算墨迹**"——两类不同。

### 13.1 半透明叠绘的边缘不是纯色

光标、阴影、焦点环都是**叠绘**：中心饱和、边缘是淡彩。
用"饱和度阈值"找光标时，**边缘排不掉**；用"避开光标列 ±8px"也排不到
（实测边缘落在光标列外 **10px**，色值 `(212,196,224)` 这种淡紫）。

后果：那些像素被当成墨迹，把"墨迹顶"读到行盒顶上，得出**"上留白 0.00"这种假数**
（我据此错误判断过一轮"文字戳出带外"）。

**做法**：先定位叠绘物，再**向两侧扩到离开其颜色边界、再各留 12px**，整段排除。

### 13.2 探针列必须落在"永远空白"处

量行底纹时把探针放在编辑器中部 ⇒ 撞上文字，把字色当成底色。
选**编辑器最右侧**（内容再长也到不了那里）。同理量卡片背景要避开标题。

### 13.3 行号槽里有分隔线

量"行号文字多高"时取样窗含了行号槽的分隔线 ⇒ "墨迹高"恒等于整带高（实测 34px）。
**取样窗前先看一眼该列里有什么**（本仓 `tools/row_ink_probe.py` 把窗口与排除列写成了常量）。

### 13.4 判据必须自适应就地底色

固定"暗于 70 = 墨迹"会把**深色按钮整片**当成墨迹；行号（灰）与代码（彩色）
也要不同阈值。**就地采样底色**，不用主题变量推（组件会再混合一遍）。

---

## 14. 验证要读**被测对象自报的值**，不要信旁路探针

实测（2026-10-07）：探针报 `origin_y = 4.13`，而应用屏上偏 6px。
根因是**探针与应用不共享同一份实现**——`layout_line` 是头文件 inline，
而增量构建按 mtime 判定，复用了缓存的 `.o`，两个二进制里是**不同版本**的 inline 函数。

**屏幕上看到的是应用的值**，所以：

* 核验界面几何，读**组件属性面**自报的值（本仓 `CodeEditor` 的
  `line_height` / `text_offset` / `caret_top` / `ink_height` / `baseline`）；
* 探针只用于**建立/校验口径**，不用于回答"应用现在是什么状态"；
* 两者矛盾时，先怀疑**二进制不同源**（清 `build/<档>` 全量重建再比）。
