# 格斗 · 强化学习训练机器人

> 这份文档只讲一件事：**怎么用 RL 训出一个真的能上场的格斗机器人**，以及
> 这条路上踩到的每一个坑。示例本体（操作/分层/控制通道）见 `README.md`。

## 结论先看

| 策略 | 对 normal 对手胜率 |
|---|---|
| 随机策略 | 0.0% |
| **手写 AI（内置）** | 7.5% |
| **PPO 训练后** | **80.2%** |

同频评测（决策间隔 1 帧）、同种子、240 局。两条基线由 `gedou_rl --eval` 用与策略
**完全相同的环境**跑出——不是"挑好看的数字"。

## 一条命令跑通

```bash
st build gedou_rl                                   # 采集/评测工具（C++）
py -3 tools/gedou_balance_check.py                  # ① 先体检：有没有“无脑必胜”
py -3 tools/gedou_rl_train.py --rounds 24 \
     --episodes 320 --eval-episodes 240 --entropy 0.05   # ② 训练（约 2 分钟）
py -3 tools/gedou_rl_plot.py                        # ③ 出训练曲线
./build/dev/bin/gedou --policy examples/gedou/policy-ppo.json   # ④ 进游戏打
```

## 架构：逻辑只有一份

```
tools/gedou_rl (C++)  ──采集经验(二进制)──>  tools/gedou_rl_train.py (torch, PPO-clip)
        ↑                                                  │
        │                                                  ↓ 导出权重
        └────── --eval 胜率 ──── policy.json ────> 游戏内 PolicyNet 推理
```

**绝不在 Python 里重实现战斗逻辑**。判定/帧数/伤害全在 `examples/gedou/fight.cpp`，
Python 只做一件事：读经验、算梯度、导出权重。这样"训练时的规则"与"游戏里的规则"
在结构上不可能分岔。

三层各自的落点：

| 层 | 文件 | 关键点 |
|---|---|---|
| 契约 | `rl_env.hpp`（观测/动作/奖励） | `--schema` 导出，Python 读它校验维度，**不手抄** |
| 环境 | `rl_env.cpp` | 动作节流、开局间距随机、对手换种子 |
| 推理 | `policy.cpp` | 纯 JSON 权重 + 定长 MLP（6k 参数），游戏与评测共用一份 forward |

## 训练链路里必须知道的六件事
### 1. 先体检，再训练

`gedou_balance_check.py` 跑 8 个固定动作 × 3 档难度。**任何一个固定动作胜率 ≥ 90%
就是"无脑必胜"**，此时训练毫无意义——RL 只会更高效地利用那个漏洞。

本项目的实测教训：训练前"一直按蹬腿"对三档难度都是 100% 胜率（打满 1000 伤害、
自己一滴血不掉），而手写 AI 只有 21%。在这种环境里训出来的"高手"，强的是漏洞。

### 2. 动作节流不装，训练必然退化

策略在每个可行动帧都会被问一次，而攻击在游戏里是"按一次出一招"。允许每帧重新
触发攻击 ⇒ "一直按踢腿" == "无限连踢腿"。实测该策略 **100% 胜率、连续重复率 98.1%**。

环境里两道约束（`RlEnv::Config`）：

- `frame_skip`：策略每 N 帧才被真正问一次，其余复用上次动作；
- `attack_cooldown`：按**招式自身总帧数**算冷却（统一小数会让"最短那招"变成最优解）。

> 公平性：默认 `frame_skip=1` 与手写 AI 同频。若给策略 4 帧一次而手写 AI 每帧一次，
> "胜率更高"里混着"对手被限制了反应速度"。

### 3. 训练/推理必须是同一个网络

`gedou_rl_train.py` 每次导出权重后自动跑 **`--forward-probe`**：把同一批输入同时喂给
torch 与 C++，逐值比对（阈值 1e-4，实测 1e-8 量级）。不一致就直接中止并报错。

没有这道护栏时，"训练收敛、进游戏不会打"这类问题只能靠盯着胜率盲猜。

### 4. 观测要覆盖现场会出现的分布

三个真实翻车，都是"训练分布没覆盖"：

| 症状 | 根因 | 修法 |
|---|---|---|
| 进游戏站住不动 | 训练固定 200px 开局，现场宽窗口初始 428px | 开局间距随机 90~430px |
| 每帧出腿但永远打空 | 训练里"出招但够不到"不扣分 | `whiff_penalty` |
| 对手不动时它也不动 | 训练对手（脚本 AI）总是主动靠近 | `idle_opponent_ratio=0.3` + `passive_range_penalty` |

> 第一条的教训最重要：**评测 80% 胜率不等于能上场**。评测环境里对手会走过来，
> 现场玩家站着不动——两者的差异完全不体现在胜率上。

### 5. 游戏侧要同步动作节流

如果游戏里不加冷却，策略每帧输出攻击，角色会一直卡在起手段——表现是"机器人站着
摆姿势"。`GameView::opponent_decision` 用**与训练完全相同的公式**（招式总帧数）
复现这套节流。

### 6. 超参：熵系数是本任务最敏感的一个

| 熵系数 | 结果 |
|---|---|
| 0.01 | 24 轮后熵从 2.08 → 0.89，锁死单招，胜率**反降**到 14% |
| 0.05（默认） | 熵稳定在 ~1.9，胜率稳定爬升到 80% |

评测局数同样关键：120 局时单局就是 0.8%，曲线在 0%~45% 之间跳，看着像"训练失败"。
默认 240 局，定论看最后翻倍复核值。

## 契约

### 观测（20 维，自我中心）

```
self_hp, opp_hp, self_meter, opp_meter,
gap, gap_near, gap_mid,                 # 距离 + 是否在轻拳/重拳触及内
facing,                                 # 对手在正/背面（±1）
self_ready, opp_ready, opp_attacking, opp_move_active,
self_phase_{startup,active,recovery},
opp_guard, opp_combo,
self_cornered, opp_cornered,
time_left
```

**自我中心**（不含世界坐标）：一张网络同时打左右两侧，不会"只会打一边"。
**不做逐样本标准化**：训练集统计量进不到游戏里的单帧推理。

### 动作（8 个离散）

`idle / forward / backward / guard / light / heavy / kick / special`

### 奖励

| 项 | 权重 | 为什么 |
|---|---|---|
| 造成伤害 | +1.0 × (伤害/对手上限) | 主轴（胜负由血量决定） |
| 承受伤害 | −0.85 × (伤害/自己上限) | 略怕换血 |
| 命中 | +0.35 | 加速学习 |
| 赢 / 输 | +6 / −6 | 终局 |
| 空挥 | −0.03 | 见坑 4 |
| 龟缩（防御且没挨打） | −0.02 | 不加则"一直按防御"的随机策略胜率 99.5% |
| 远距离不压上 | −0.02 | 见坑 4 |

## 工具一览

| 命令 | 作用 |
|---|---|
| `gedou_rl --schema` | 打印契约（观测/动作/奖励） |
| `gedou_rl --selfplay --out data.bin` | 采集经验（~120 万步/秒） |
| `gedou_rl --eval --policy F` | 评测策略胜率 |
| `gedou_rl --eval --random` / `--script-ai` / `--constant kick` | 三条基线 |
| `gedou_rl --action-histogram` | 策略在做什么（含**连续重复率**） |
| `gedou_rl --trace` | 逐帧轨迹（谁在动、什么动作、什么时候命中） |
| `gedou_rl --forward-probe` | 前向自检（训练脚本自动调用） |

`--trace` 与 `--constant` 是排查这类问题的**唯一有效手段**。实测：`--trace` 一眼看出
"玩家 900 血全程未损、对手只在走位"，比盯着胜率猜快一个数量级。
（注：早期 `--trace` 里 `--constant` 分支写漏了，跑的是随机策略——**诊断工具用错输入
会把人带向反方向**，所以现在两条路径共用同一份下标解析。）

## 已知限制

- 观测里的距离按 **300px 归一**，训练场地固定 1040 宽；游戏窗口差异大时策略的
  距离感会偏（已用 `start_gap` 固定缓解，但没有从根本上做尺度归一）。
- 训练对手是手写 AI + 打桩，**不是自我对弈**。自我对弈会更强的同时更难复现。
- 没有 value 头进推理（critic 只在训练进程里），因为推理侧要与导出的权重逐层对应。

## 验证状态（实话）

| 层面 | 状态 |
|---|---|
| 训练可复现、胜率可重测 | ✅ 同种子两跑逐值一致；胜率可用 `--eval` 任意重测 |
| 前向一致性（torch ↔ C++） | ✅ 训练时强制逐值校验（阈值 1e-4，实测 1e-8） |
| 35 条单测 + 7 组 e2e | ✅ 全绿 |
| 游戏内真实加载并作战 | ✅ 截图确认（主动接近→连击 18 → K.O.） |
| **逆向验证（回退→变红）** | ⚠ **部分不可验**。`observation-dim-drift` 与 `forward-matrix` 成立；
`egocentric` / `reward-signs` / `cooldown` 三条目前**无法**用回退证明 |

最后一条的原因不在 RL 代码，而在**构建系统**（已记入 `docs/BACKLOG.md` P1）：
`st build` 判断“测试二进制是否过期”时只看 `tests/*_test.cpp` 自身的内容哈希，
而不看它们 `#include` 进来的实现文件 —— 于是“把实现改回去 → 重编 0 → 测试仍绿”。
取证：`.d` 依赖清单与 `.meta` 哈希都记录正确，问题在那个更粗的“测试源快照”判据；
`--force` 全量重编也一样。

这三条断言本身是写对的（手工改代码验证过它们能变红），但**在构建缺陷修好之前，
它们不能被自动回退验证覆盖**。不把它们当成“已验证”。
