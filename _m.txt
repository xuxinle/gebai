feat(shell): 窗口先用软件画布秒开，后台备好 GPU 后再升级

用户要求："能不能先用软件渲染把窗口立刻弹出，等后台 GPU 设备就绪再切"。
做成框架能力（`AppOptions::defer_gpu`），不是某个应用的局部 hack。

## 为何有效（先量后做）

| 渲染器 | 窗口出现 |
|---|---|
| software | 147~163 ms |
| gpu | 498~549 ms |

而软件画布的稳态帧只要 1.59 ms（paint 0.55 / present 1.03）——完全能先
支撑界面运行。那 350 ms 全是 GPU 初始化（建 D3D11 设备 ~330 ms +
着色器管线 ~55 ms），它原本发生在窗口可见之前。

## 实现

1. `AppOptions::defer_gpu`（默认 true）+ 判据 `defer_gpu_effective()`；
2. `create_window` 在 defer 时先分配软件画布并立即返回；
3. 后台线程只做「建设备 + 预热管线」。`CreateSwapChain` 不能放后台
   （它内部要跑消息泵，必须与窗口同线程），所以 swapchain 留在主线程；
4. `framebuffer()`（帧边界）检测就绪 → 建 GPU 画布 + presenter 并换型。
   放帧边界与尺寸重建同一条时序纪律，避免"画在旧画布、present 新画布"；
5. 析构里 join 后台线程（它持有 this 引用）。

## 实测

```
窗口出现: 115~132 ms      （改前 498~581 ms）
UI 响应:  124~150 ms      （改前 957~2585 ms）
GPU 设备后台就绪：373 ms
已升级到 GPU 画布：2.0 ms
renderer = gpu，present_skipped = 0
```

升级后截图与纯 GPU 启动逐像素一致（无错乱、无空白）。

## 顺带修掉两个真缺陷

1. **相期的 `--renderer` 完全失效**：`Options` 里根本没有这个字段，
   解析器也不认。上一轮所有"软件模式"的测量实际都在跑 GPU。

2. **`renderer = "auto"` 会让 `defer_gpu` 静默失效**（auto 非空 ⇒ 被当成
   "显式指定"）。相期最初就踩了：开关看着是开的，窗口仍 530 ms，
   且日志里一句提示都没有。判据已抽成 `defer_gpu_effective()`，
   由 5 条回归测试钉住并做过逆向验证（去掉 renderer.empty() 立刻 3 条变红）。

3. 相期连 agent 的握手读曾是阻塞无超时——"连一个没监听的端口"实测要
   ~450 ms 且在主线程上。已改为后台线程连接，主循环只看结果。

## 未覆盖
