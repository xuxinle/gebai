# 企业微信能否像飞书那样接入拟人模式

> **状态：调研结论，未实施。**
> 触发问题：拟人模式能否照飞书的做法（长连接收消息 + 渠道出站）接入企业微信。
> 结论：**技术上可接，但拟人的核心诉求（在场感）满足不了，故不实施。**

## 结论

**拟人模式的群聊能力无法迁移到企业微信。** 不是工程难度问题，是平台协议的能力边界：
企微智能机器人在群聊里**只有被 @ 才能收到消息**，没有任何配置项能打开全群可见。

具体到本仓库，`speaker-filter` 那套机制（`packages/persona/src/speaker-filter.ts`）
在企微群聊里会整体失效——它建立在「收得到全部消息」这个前提上：

| 决策 | 飞书 | 企微群聊 |
|---|---|---|
| `record`（写入上下文） | 全群消息一律录入 | **只有被 @ 的那条能录入** |
| `deliver`（触发一轮） | 按发送者分类决定 | 只有被 @ 这一种情形 |

结果差别不是"覆盖率低一点"，而是**人格从"在场旁听"退化成"被叫到才存在"**：
每次被 @ 都是一次冷启动，它不知道群里之前说过什么。这与"拟人"直接冲突。

## 平台的硬约束（核实自企业微信开发者中心）

| 通道 | 收 | 发 | 群里不被 @ 能收吗 |
|---|---|---|---|
| 智能机器人 · 长连接 API | WebSocket 推送 | 同一连接上回复/主动推送 | **不能** |
| 智能机器人 · 回调地址 | HTTP 回调 | 被动回复 | **不能** |
| 自建应用消息回调 | 用户给应用发消息 | 应用消息 | 不能（点对点语义） |
| 群机器人消息推送 | **不收** | webhook 单向 | 不适用（只能发） |

官方《接收消息》文档列举的全部触发场景中，群聊场景**无一例外都以 @ 为前提**，
不带 @ 的只有单聊。这是协议设计，非配置项。

其余与拟人相关的差异（供日后复评）：

- **没有"用户身份读历史"**。飞书源的核心价值之一是用户令牌能读机器人不在的群
  （见 `packages/persona/docs/feishu-source.md`），企微无等价开放能力。
- **一个机器人只能一条长连接**，新连接订阅即踢掉旧的——与飞书同款的互踢风险，
  若日后接入需照 `packages/server/src/core/session/persona-feishu-deps.ts` 做启动期撞车判定。
- **主动推送要求"用户先在会话里说过话"**，定时播报类场景需要降级对外通道。
- **`chatid` 仅群聊返回**，单聊出站须填用户 `userid` + `chat_type=1`。

## 架构层面：限制不在扩展点，在平台

需要澄清一点，避免日后误判为"框架不支持"：**渠道扩展点本身完全够用。**
企微若只是做单聊收发，放一个 `custom/channels/wecom.ts` 即可，三面（`verbs` / `observes` /
`listens`）在同一个文件里声明，不需要改任何核心代码——路由、幂等、归属全在桥接层
（`packages/channels/src/bridge.ts`）统一裁决。

**卡住的是"在场"，不是"接入"。** 这两件事要分开记，否则会误导后续决策。

## 可行的边界

| 场景 | 可行性 | 说明 |
|---|---|---|
| 单聊助手 | ✅ 体验完整 | 无需 @，无需额外资质，可直接照飞书渠道的结构实现 |
| 群聊"点名应答" | ⚠️ 能做但不拟人 | 需在正文尾部明确告知模型"本群仅在被 @ 时可见消息"，否则它会拿残缺上下文编造前情 |
| 群聊旁听 | ❌ 不采用 | 需依赖付费合规类产品（按人数采购、员工强制告知），性质是把助手建在会话监控之上；与本项目定位不符，不展开 |
| 协议模拟 | ❌ 不做 | 违反服务条款，且客户端升级即失效 |

## 若日后重启评估

先验证再谈工期，三条按序确认：

1. 目标企业的机器人后台是否有「智能机器人 · API 模式」入口（部分企业未开放）；
2. 群聊 @ 时 `text.content` 是否带 `@名字 ` 前缀（需剥离，否则正文带噪音）；
3. `from.userid` 是否明文——仅当机器人创建者为超级管理员时明文，否则是加密 userid，
   需自建应用 `access_token` 转换，这直接影响"这条是不是用户本人发的"判定。

第一条不过，其余无需再谈。
